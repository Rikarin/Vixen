# Projects that pack and whose public surface `CheckApi` does not read.
#
# CheckApi's coverage is a glob (build/Build.Api.cs), and a glob says nothing at all about what
# it does not match. An assembly outside it still produces a .nupkg, so every addition, every
# signature change and — the half that breaks a consumer without breaking anything here — every
# silent removal in it passes with nothing to approve it, while the target prints
# `Checking the public surface of N assemblies` and succeeds. That is the shape this repository
# keeps rediscovering: a gate reporting success on work it did not do.
#
# This file is the other half of the decision. The set the gate skips is written down, so that
# joining it is a reviewed line in a diff rather than silence, and ApiCoverageTests asserts the
# list and the tree agree in BOTH directions:
#
#   * a project in Vixen.slnx that packs, is not a test/generator/analyzer and has no
#     PublicAPI.Shipped.txt beside it, and no line here — fails,
#   * a line here naming a project that no longer exists, no longer packs, or now has a
#     baseline — fails, because a stale exemption is how a list like this stops meaning
#     anything.
#
# One line per project: its path from the repository root, whitespace, and the reason token.
#
# ⚠ Nothing here is an exemption somebody argued for on the merits. Twenty-three of the
# thirty-one lines are #641, which is open and asks the opposite question: a package is a
# promise, so either these are covered the way Core/ is, or they should not be packing.
#
# ⚠ And the undecided set GROWS on its own, which is the argument for answering rather than
# deferring: it was twenty-one, and Vixen.Editor.TextureGraph and Vixen.Editor.Texturing joined
# it by being added under Editor/ — the profile packs them by default, so nobody chose to ship
# them and nobody had to. This assertion going red is the only reason that was noticed at all,
# and adding the two lines is deliberately not an answer to #641.
#
# ⚠ Before answering it, know what "cover them" costs, because it is not twenty-three baselines.
# A PublicAPI baseline is read by TWO gates. CheckDocsCoverage takes every tracked
# PublicAPI.Shipped.txt and PublicAPI.Unshipped.txt in the repository — a glob over tracked
# files, not CheckApi's project list (build/Build.DocsCoverage.cs, BaselinedTypes) — and fails
# any type in one that has neither a guide page nor a line in docs/DocsExempt.txt. So a
# baseline is an enrolment in the documentation gate as well, and #686 is the same fact from
# the other side: the types CheckDocsCoverage was written to catch are green precisely because
# their projects keep no baseline. Covering the twenty-three would move on the order of a
# thousand types (1 052 by a grep for public type declarations under the twenty-three, which is
# a source-level count and so a floor, not a total) from silence into CheckDocs, each owing a
# page or an exemption line — on top of the twenty-three Release-generated baselines. That is
# the real price of option 1, and it is why "just generate the baselines" is not a small change
# an agent lands on the way past.
#
# ⚠ Two of these lines are not free to take the other option, and that had never been measured.
# "Cover it or stop packing it" reads as a choice between two, and for Vixen.Editor.Ui and
# Vixen.App it is a choice between one: a covered package already depends on them, and a
# ProjectReference without PrivateAssets=all becomes a <dependency> in the .nuspec. Vixen.Editor.Plugin
# — the single Editor assembly CheckApi names, and the one doc 11 asks a STRICTER compatibility
# policy of than anywhere else in the editor — references Vixen.Editor.Ui; Vixen.Live.Realm
# references Tools/Vixen.App. So the strictest promise in this repository is today only as strict as
# an assembly approved by nobody, a removal in Vixen.Editor.Ui breaks a plugin author's build while
# both gates pass, and un-packing either one leaves a published package declaring a dependency that
# does not exist. ApiCoverageTests.APublishedDependencyOfACoveredPackageIsCoveredToo holds that set
# at exactly these two, in both directions.
#
# ⚠ And the order the tooling imposes is the dangerous one: `Vixen.ApiCheck --update` writes the
# baseline beside the project, and Build.Api.cs's glob is a separate edit. A baseline added
# without the glob is read by CheckDocsCoverage and NOT by CheckApi — that half is still true
# and is a reason to make both edits in one commit. What is no longer true is the rest of it:
# ApiCoverageTests used to decide "covered" by the presence of the file alone, so it reported
# such a project as covered and demanded the line here be deleted. It now requires the glob to
# match as well, and EveryBaselineSitsWhereCheckApiLooks names a baseline the glob does not
# reach instead of hiding it. That was #809.
#
# ⚠ RECOMMENDED ANSWER, and the measurement nobody had made: NOTHING HAS EVER SHIPPED. There is
# no publish workflow — .github/workflows holds ci.yml, docs.yml and nightly.yml and none of them
# runs `dotnet nuget push`; `Pack` writes artifacts/packages and stops, and `dotnet nuget push`
# appears in this repository only in docs/plan/12, which is intent. docs/manual/building-a-game-
# and-a-server.md:31 says it outright — "Until the packages are on nuget.org you need a
# nuget.config next to the project pointing at a [local feed]". So "a package is a promise" is
# today a promise to nobody, every one of these thirty-one packages is at version 0.1.0, and the
# cost of answering #641 will never again be as low as it is before the first push. That is an
# argument for deciding now rather than for deferring further.
#
# ⚠ And there IS a first-party statement of what a consumer installs, which nobody had read as
# one: Tools/Vixen.Templates. What `dotnet new` scaffolds is the only place this repository tells
# an outsider which packages to reference, and across all six templates that is ten names —
# Vixen.App, Vixen.Engine, Vixen.Live.Abstractions, Vixen.Live.Realm, Vixen.Net,
# Vixen.Net.Transport.Udp, Vixen.Rendering.PostFx, Vixen.Ui.Desktop, Vixen.Ui.Desktop.HotReload
# and exactly ONE under Editor/: Vixen.Editor.Plugin, which is precisely the one CheckApi already
# covers. Twenty-three Editor assemblies pack and the templates ask for one of them.
#
# So the recommendation, which is a recommendation and not a decision — the owner's, per #641:
#
#   * Option 2 for the twenty-one `editor-undecided` lines that are neither Vixen.Editor.Plugin
#     nor its published dependency: set IsPackable=false. They are consumed in-process by the
#     editor, no template references them, nothing installs them, and the 1 052 documentation
#     decisions option 1 drags in are owed to nobody. Best expressed once in the TOOLING profile
#     in Directory.Build.props rather than twenty-one times, because that also fixes the defect
#     the ⚠ above records: a project added under Editor/ currently packs before anyone has an
#     opinion, so the undecided set grows by default and only this file notices.
#   * Option 1 for Vixen.Editor.Ui and Tools/Vixen.App, where option 2 is not available at all —
#     both are published dependencies of covered packages, and Vixen.App is in the template list
#     besides, so it is a package an outsider is told to install. Two baselines, not twenty-three.
#   * Vixen.ShaderCompiler then falls out by the reasoning already written under
#     `library-undecided`: un-pack the Editor set and its last packable consumer goes with it.
#
# The counter-argument, stated fairly: an editor that means to be extended out-of-process, or a
# marketplace of editor extensions, needs these packable and then option 1 is right — and that is
# a product question about what this repository sells, which is why it is not being answered here.
#
# Reason tokens:
#
#   editor-undecided   Editor/. The TOOLING profile in Directory.Build.props sets no IsPackable,
#                      so every Editor project takes the SDK default of *true*; only .App, .Host
#                      and .Testing opt out, and the two generators are excluded by the
#                      compiler-plugin profile. ⚠ "Editor/ is applications, so it does not pack"
#                      does not survive contact with the tree: all of these carry a
#                      <Description>, PackageTags and a PackageReadmeFile, which is a project
#                      that means to ship rather than an accident of the default.
#                      Vixen.Editor.Plugin is the one CheckApi names, and is not here. (#641)
#
#   library-undecided  A packable library outside Editor/ with a real referenced surface and no
#                      baseline — the same condition Vixen.Raven was in before it was covered.
#                      ⚠ This refutes the Coverage section of Tools/Vixen.ApiCheck/README.md,
#                      which says Tools/ "ships to nobody": seven Tools projects declare
#                      IsPackable=true, and two of them are libraries a consumer compiles
#                      against. (#749) ⚠ The two are not one question: Vixen.App is a published
#                      dependency of Vixen.Live.Realm, which IS covered, AND one of the ten
#                      package ids the six `dotnet new` templates put in a stranger's csproj, so
#                      only "cover it" is available there by two independent routes — it is not
#                      merely referenced by six samples by path.
#                      Vixen.ShaderCompiler is on neither route and is reachable from no covered package
#                      — its consumers are two dotnet tools (which bundle rather than depend),
#                      three samples, the tests, and Vixen.Editor.ShaderGraph and
#                      .TextureGraph, both of which are `editor-undecided` above. So #749's second
#                      half is downstream of #641: cover the Editor set and ShaderCompiler becomes
#                      a published dependency too; un-pack it and ShaderCompiler is genuinely free.
#
#   tool-command-line  Packed with PackAsTool. What a `dotnet tool install` promises is a
#                      command line and its arguments, not a type; the assembly is an
#                      implementation detail nothing references. A CLI-surface gate would be a
#                      different instrument from this one.
#
#   no-assembly        IncludeBuildOutput=false — the package is MSBuild logic or template
#                      content and carries no lib/, so there is literally no surface to read.
#                      This is the only token on the list that is a settled answer.
