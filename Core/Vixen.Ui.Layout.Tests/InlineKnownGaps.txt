# Inline formatting — what doc 43 § B3 landed, what fragmentation and anonymous block boxes landed
# after it, and what none of the three did.
#
# ⚠ THIS FILE IS NOT SHAPED LIKE ITS THREE SIBLINGS, AND THE REASON IS THE WHOLE STORY.
#
# `KnownGaps.txt`, `BlockKnownGaps.txt` and `GridKnownGaps.txt` are lists of FIXTURE NAMES: a corpus
# of browser-recorded answers exists, most of them pass, and each line names one that does not. That
# file shape is only possible because somebody else already wrote down the right answers.
#
# There is no inline corpus. Not a thin one — none. Verified by enumeration across all eight of
# Taffy's XML files rather than assumed:
#
#   · The `display` attribute takes exactly five values in the whole corpus:
#       block 2 276 · flex 764 · flow-root 12 · grid 2 496 · none 68
#     Not one `inline`, `inline-block`, `inline-flex` or `inline-grid`.
#   · The string "inline" occurs 12 times and every occurrence is a TEST NAME about a grid's inline
#     axis (`grid_overflow_inline_axis_{hidden,scroll,visible}__*`).
#   · The string "vertical" occurs 8 times outside `vertical-lr`, and every occurrence is a test
#     name too (`rounding_inner_node_controversy_vertical`, `grid_relayout_vertical_text`).
#   · Yoga's 534 are the same: its style surface has no inline keyword and no `vertical-align`.
#
# So this file lists RULES rather than fixtures, and every entry says which of three things it is:
# implemented and tested, deliberately absent with a reason, or absent for want of an oracle.
#
# The oracle that does exist is web-platform-tests (BSD-3-Clause), re-expressed rather than
# translated in `InlineFormattingTests`, exactly the way `OrderTests` re-expresses WPT's `order`
# tests. See the last section for why most of WPT's inline suite still cannot cross.

# ══ FRAGMENTATION — LANDED, and the invariant it broke is worth keeping written down ════════════
#
# ⚠ THIS SECTION USED TO BE THE BOUNDARY. It said that every algorithm in this store preserved an
# invariant it never had to state — ONE NODE PRODUCES ONE BOX — and that CSS Display §2.2's
# non-replaced `inline` box breaks it, with nowhere to put the second fragment. The first half is
# still true and is why the store is shaped the way it is. The second half is not, any more.
#
# What it cost, so that the next algorithm can compare: ONE ARENA AND THREE INTS (offset, count and
# capacity, exactly as `ChildArena` and `TrackArena` are addressed), and NOT a change to any
# existing consumer. `FragmentArena` is the same shape as `TrackArena` — grid needed
# variable-length INPUT, this is variable-length OUTPUT — and `LayoutResult` carries a handle into
# it. The thing that made it additive rather than a migration is the zero default:
#
#     FragmentCount == 0  means  "one box, and it is Position and Dimensions, exactly as before".
#
# So `GetLeft` was not touched, the absolute walk was not touched, and neither was any of the four
# properties in `Vixen.Ui/UiElement.cs` that every hit test and draw list in the engine goes
# through. ⚠ AND WHEN THE COUNT IS NON-ZERO, `Position` AND `Dimensions` HOLD THE UNION of the
# fragments — which is not a fallback but CSS 2.1 §10.1's own answer, since the containing block of
# an absolutely positioned descendant of an inline box IS the bounding box of its first and last
# fragments. That is why the absolute walk needed nothing.
#
# ⚠ THE CLAIM THAT A LINE BOX ALLOCATES NOTHING SURVIVED, and it was the thing most at risk. A line
# used to be a contiguous range of `ChildIds`; it is now a contiguous range of a flattened stream of
# Open/Atomic/Close entries, because a span is not ON a line — its children are, and it contributes
# only its two edges. The stream and the fragment scratch are watermarked buffers reused across
# passes, so `LayoutPassTests`'s zero-byte gate still holds with a span re-fragmenting every frame.
# `A_fragmenting_span_re_laid_every_frame_allocates_nothing` is that gate for this path.
#
# ⚠ AND NOTHING OUTSIDE THIS ASSEMBLY READS A FRAGMENT, which is a bigger hole than any row below.
# `GetFragment` and `GetFragmentCount` have no caller anywhere in the tree except
# `InlineFragmentationTests`: no painter, no hit test, no consumer of any kind. `DrawListBuilder.
# EmitBody` takes ONE rectangle from `UiElement.Width`/`Height`, which for a fragmented node is the
# UNION of its fragments — the right answer to §10.1's containing-block question and the wrong one
# for a background. On a ragged second line that is a visible block of colour where there is no
# content, and the hit test agrees with it, so a click lands there too.
#
# The two halves are pinned as they stand in `Core/Vixen.Ui.Tests/InlineFragmentPaintingTests.cs`,
# which asserts what Vixen does and records what Chrome does beside it — a span of 30 + 60 then 60 in
# a 100-point line is painted (0, 0, 90, 40) here and (0, 0, 90, 20) plus (0, 20, 60, 20) there.
# ⚠ Those tests SHOULD FAIL and be inverted when a fragment-walking draw list lands, and the hit test
# has to move with the painter rather than after it: `DrawListBuilder`'s own remark makes paint order
# and hit-test order agreeing the guarantee that a click lands on what is drawn, so walking fragments
# in one and not the other breaks it on exactly the wrapped inline the feature is for.
#
# ⚠ Worth knowing before writing that fixture: a `display: inline` element only fragments when its
# CONTAINER runs the block or inline algorithm. This store's default display is flex, so a plain
# wrapper makes the span a flex item, stretches it, and it never fragments at all — the pin above
# needs `display: block` on the wrapper and looks for a while as though `display: inline` were being
# dropped by the bridge, which it is not.
#
# Covered by `InlineFragmentationTests`. What remains is SCOPE — a limit of the producer, not of the
# representation, which holds any number of fragments for any node:

nested non-atomic inline boxes    a `display: inline` box INSIDE another one is still laid out
                                  atomically. One level of flattening, not a recursion. What is
                                  missing is the rebasing of a union inside a union, not somewhere

# ══ ANONYMOUS BOXES — LANDED, and the estimate that was right is worth keeping written down ═════
#
# ⚠ THIS SECTION USED TO BE UNDER "DELIBERATELY ABSENT", and the reason it moved is that the
# blocker recorded here was overstated and somebody said so before building anything. The old text
# said inventing an anonymous box means "either allocating nodes during layout or teaching the walk
# to address something that is not a node", as though both were structural. The correction, written
# down by the agent that built `FragmentArena` and CONFIRMED before this was implemented, was:
#
#   An anonymous block box takes INITIAL VALUES for every non-inherited property, so it has no
#   background, no border, no padding, no margin and no event target. It is never painted and never
#   hit-tested. It therefore needs NO STORED RECTANGLE AT ALL — only the ability to run a line walk
#   over a SUB-RANGE of a container's children and report a height, which `MeasureLine` and
#   `PlaceLine` already take.
#
# ⚠ THAT HELD EXACTLY, AND THE MEASURED PRICE WAS FOUR PARAMETERS AND NO STORE CHANGE. `LayoutResult`
# did not grow a field, `FragmentArena` was not touched, `GetLeft`, the rounding pass and the
# absolute walk were not touched, and nothing in `Vixen.Ui` was told anything. What changed:
#
#   · `BuildInlineItems`, `HideAndPositionOutOfFlow`, `WalkInlineLines` and
#     `DetermineInlineContentWidth` each take a child sub-range instead of a whole child list.
#   · `WalkInlineLines`'s `insetTop` became `contentTop` — the anonymous box's top edge, which for a
#     whole-container walk is still the container's top inset.
#   · `WalkBlockChildren` and `DetermineBlockContentWidth` detect a run and hand it over.
#
# ⚠ AND IT IS ONE DIRECTION FROM FRAGMENTATION RATHER THAN THE SAME ONE. Fragmentation is one node
# to many boxes; an anonymous box is a box with NO node. The fragment arena did not help and was
# never going to: storing an anonymous box as a fragment of some nearby node would give it that
# node's style, which is wrong. The two are independent and they compose — a span fragmenting inside
# an anonymous block box needed no code, and `A_span_inside_an_anonymous_block_box_still_fragments`
# is the assertion that says so.
#
# Three things that were decisions rather than derivations, so that the next reader can disagree
# with them on purpose:
#
#   · A `display: none` or out-of-flow child does NOT split a run — neither is block-level content,
#     which is what §9.2.1.1 breaks a run at. A run's END is trimmed back past them, so that a
#     trailing absolute sibling gets the static position AFTER the run rather than the run's own top.
#   · An anonymous block box is NEVER a collapse-through box, however short it comes out, because by
#     construction it holds at least one line box — and §8.3.1's collapse-through is exactly "nothing
#     separates this box's two margins". Its own margins are zero, so it adds to no adjoining set.
#   · A mixed container reports the LAST run's baseline as its own, and only when that run is its
#     last in-flow content. §10.8.1 wants the last line box in normal flow; after a real block-level
#     child that line box is somewhere inside the child and nothing here can reach it, so the answer
#     falls back to CSS Align §9.3's synthesis, which is what a block container already did.
#
# Covered by `InlineFormattingTests` (seven tests, headed by
# `Mixed_content_wraps_each_inline_run_in_an_anonymous_block_box`, which is
# `Mixed_content_stacks_because_there_are_no_anonymous_boxes` inverted) and by two in
# `InlineFragmentationTests`.

generated boxes (::before/after)  doc 43's A12. ⚠ ITS PRECONDITION IS NOW MET AND ITS OWN BLOCKER IS
                                  NOT — worth stating plainly, because the row above moving makes
                                  this look closer than it is. A12 was never blocked on
                                  fragmentation; it was blocked on anonymous boxes, and those have
                                  landed. What is left is the half that was always A12's own: a
                                  generated box has a STYLE of its own, so it needs a second style
                                  slot rather than a second rectangle, and the sub-range machinery
                                  above serves a run of REAL children and has nothing to say about
                                  a box that is not one of them. So this is reachable now, and it
                                  is not started. A12's estimate should be re-read against this
                                  section rather than revised on the strength of it.


# ══ FLOATS BESIDE LINES — LANDED, and the oracle had to be built before the code ════════════════
#
# ⚠ THIS SECTION USED TO BE ONE ROW IN THE LIST BELOW, and that row's own text said it had got
# BIGGER rather than smaller. The reason it could is worth keeping written down, because it is the
# same trap the rest of this file is about.
#
# Floats were implemented, `LayoutTree.Floats.cs` kept a live exclusion list per formatting context,
# and all 92 float fixtures across the Taffy corpora passed. None of it reached line layout:
# `WalkInlineLines` asked the exclusion list nothing, so a line box beside a float was laid out at
# the container's full inner width and ran straight under it — §9.5's main clause, and the only
# behaviour a non-specialist would name if asked what a float does.
#
# ⚠ IT SURVIVED BECAUSE THE ORACLE COULD NOT SEE IT. `grep -c '<text' Corpus/float.xml` is 0. All 84
# of that corpus's fixtures are block-level, so the corpus NAMED AFTER THE FEATURE could not test the
# feature's headline rule, and 92 green fixtures were evidence about placement, clearance,
# containment and formatting-context avoidance and evidence about nothing here.
#
# ⚠ SO THE ORACLE WAS BUILT FIRST, AND THAT WAS THE SUBSTANTIAL HALF. `Tools/Vixen.TaffyTestGen` was
# checked and cannot help: it vets and consolidates Taffy's own XML, and Taffy has no inline layout,
# so there is nothing upstream to generate from. The answers in `InlineFloatInteractionTests` were
# instead READ OUT OF CHROME 148.0.7778.280 — each case written as an HTML fixture, served over
# localhost, and every box's `getBoundingClientRect()` differenced against its container's. Two
# properties of those fixtures are load-bearing rather than decorative:
#
#   · every box states a `width` and a `height`, so no number depends on a font — the same property
#     that let `css-flexbox/inline-flex.html` cross and stopped the rest of WPT's inline suite; and
#   · every fixture sets `font-size: 0; line-height: 0`, which zeroes §10.8's STRUT. This store has
#     no strut (see the next section), so a Chrome line box is comparable with a Vixen one only once
#     the strut has been taken out of it. Left in, every expectation is wrong by a font metric.
#
# ⚠ AND THE FIRST RUN OF THAT ORACLE WAS WRONG, WHICH IS WORTH ADMITTING IN WRITING. The cases were
# stacked in one page as plain `div`s, so a float overflowing the bottom of one case went on
# narrowing the NEXT case's lines — correct CSS §9.5, and it silently moved two fixtures' floats 50
# points sideways. Every root is a `display: flow-root` now, which is also what a `LayoutTree` root
# is. A browser used as an oracle is still an instrument that has to be verified.
#
# What landed, all of it in `WalkInlineLines` and all of it dead when `treeHasFloats` is false:
#
#   · §9.5's main clause — a line box is shortened to the band the floats crossing it leave, and
#     goes back to full width on the first line that clears them.
#   · The band is asked for TWICE, and the second ask is not an optimisation. `FloatBandAt`
#     deliberately excludes a float whose top edge is exactly the slice's top — the strictness that
#     lets a cleared box sit flush against what it cleared — so a zero-height probe at a line's own
#     top sees NO float at all. The line is broken, measured, and re-broken against the band at its
#     real height. ⚠ THREE ATTEMPTS IS A CAP AND NOT A FIXED POINT: a narrower band can only take
#     items away, so the second answer is normally final, but a line SHIFTED past a float can find a
#     wider band and take items back. Chrome does not iterate to a fixed point either.
#   · §9.5's other clause — a line box with no room for its first item is shifted downward past each
#     float in turn "until either it fits or there are no more floats present". The second half is
#     what keeps it from being a clamp: an item wider than the container never fits any band, and
#     Chrome still puts it below the last float and lets it overflow from there.
#   · The three coordinate systems. The exclusion list is in the formatting context ROOT's content
#     coordinates, `floatOriginX/Y` hold the container's BORDER box in them, and a line box is
#     addressed in the container's own — so the query subtracts `floatOriginX + insetLeft`, and the
#     band is clamped to this container rather than to `floatContextWidth`, which belongs to the
#     root. A narrower box nested in a wider context would otherwise get a line wider than itself.
#   · RTL, which is one subtraction rather than a second case. The float's SIDE is physical and the
#     line's start edge is not, so a left float narrows an RTL line without moving where it begins
#     and a right float moves where it begins without narrowing it differently.
#   · `CalculateInlineLayoutImpl` now opens a float scope when it is a formatting context root. It
#     can never place a float of its own — `EstablishesInlineFormattingContext` refuses a container
#     with a floated child — so the scope always closes empty and §10.6.3 has nothing to say. What it
#     buys is the other half of §9.5: an `overflow: hidden` paragraph beside a float is moved aside
#     WHOLE by its parent's walk, and its lines must then be full width rather than shortened a
#     second time by a float it has already cleared. Counting the float twice is the bug.
#
# Covered by `InlineFloatInteractionTests` (18 tests). Sabotage-checked five ways, one per mechanism,
# because a single-site break proves nothing: neutering the band query reddens 16 of the 18, dropping
# the second probe reddens 17, dropping the shift-down reddens 4, dropping the line's start inset
# reddens 11, and dropping the formatting-context scope reddens exactly the one test that is about it.
#
# ══ A FLOAT DECLARED INSIDE A RUN — §9.5.1 RULES 5 AND 6, LANDED ════════════════════════════════
#
# ⚠ THIS SECTION USED TO BE TWO ENTRIES SAYING THIS WAS NOT HERE, and the smaller of the two turned
# out to be the more damaging one. The row said a float between two items ends the run and is placed
# one line low by `WalkBlockChildren` — true of a floated `block`. A floated `inline-block` did
# something else entirely: `IsInlineLevel` answers `true` for it, `StartsAnonymousRun` carried the
# float clause and `AnonymousRunEnd` beside it did NOT, so such a float was swallowed into the run as
# an ORDINARY ATOMIC ITEM. It sat on the line, advanced the pen, set the line's height, and never
# reached the exclusion list at all — §9.5 did not happen to it in any form. One clause on the run's
# start with no matching clause on the run's end.
#
# What landed:
#
#   · `InlineItemKind.Float`. A float is an entry in the flattened stream, which is what lets the
#     line walk own its placement. `BuildInlineItems` emits it ahead of the flattening test, so a
#     floated `inline-block` and a floated `block` take the same path — §9.7's blockification.
#   · `AnonymousRunEnd` no longer ends a run at a float, so the anonymous block box contains it and
#     the line walk sees it. `StartsAnonymousRun` still refuses to START one at a float, which keeps
#     `WalkBlockChildren`'s float branch reachable for a float with no line to sit on — and the two
#     answers agree there, because the flow cursor and the line top are the same number.
#   · `PlaceFloatsOnLine`, which is rule 6 and nothing else: the float's placement search starts at
#     the top of the line it was written on instead of at the flow cursor. Everything after that —
#     clearance, rule 3, the band search of rules 1, 2 and 7 — is `PlaceFloatChild` unchanged, which
#     is why two floats on one line stack sideways without new arithmetic.
#   · A re-break. Placing a float mid-line moves the band, so the line is broken again against it —
#     which moves the items written BEFORE the float. That is the half that looks wrong and is what
#     Chrome does: `a` · float · `b` `c` `d` puts `a` at x=50.
#   · A watermark over the stream rather than a range, because a re-break can move the line's end
#     backwards and a float placed twice is an exclusion that never goes away.
#   · `DetermineInlineContentWidth` charges a float to `preferred` and to `minimum` exactly as an
#     atomic item, which is the third owed row closed. A float takes room from every line it crosses,
#     so max-content is the arrangement where the float and the run share a row: a shrink-to-fit box
#     holding a 30-point float and two 50-point items is 130 wide and one line tall, where it used to
#     be 50 wide and three lines tall — it had refused to make room for a float it contained.
#
# The attempt cap went from three to five, and the two extra are for this: placing a float
# invalidates the break, the shift AND the height, so the search restarts rather than continuing.
#
# ⚠ WHAT IS *NOT* HERE, sized rather than half-built:
#
#   · A float is not pushed below the line when the ITEMS already on that line leave it no room.
#     `PlaceFloatChild`'s search consults the exclusion list only, so a float too wide for the band
#     left by earlier FLOATS drops and one too wide for the space left by earlier CONTENT does not —
#     it takes the space and the line re-breaks around it. No Chrome reading was taken for it.
#   · A float inside a non-atomic inline box. `IsNonAtomicInline` refuses to flatten a span with a
#     floated child, so such a span stays atomic and its float is an ordinary block-level one placed
#     against the span itself. Flattening it would rebase the float's position by the span's origin a
#     second time, because the line walk writes a float in the CONTAINER's coordinates. It is the
#     fifth restriction in that method's list and has the same shape as the fourth.
#   · Text wrapping around a float's staircase. A text leaf is one atomic item here and this walk
#     never breaks inside one, so a paragraph beside a float re-flows as whole leaves. Shortening a
#     leaf's first line is the fragmentation item three rows down, and it is the same blocker: there
#     must not be a second text wrapper disagreeing with `TextLayout` about UAX #14. ⚠ THIS IS THE
#     ONE ITEM OF THE THREE THAT IS STRUCTURAL RATHER THAN UNWRITTEN, and it does not become
#     available by trying harder here: `Vixen.Ui.Layout` has no font, no font size and no
#     `FontRegistry`, which is the same wall the strut is behind.
#   · `clear` on a line box, which is NOT owed and was measured rather than argued. §9.5.2 applies
#     `clear` to floating and block-level elements only, and Chrome 148 agrees: `clear: left` on an
#     `inline-block` beside a left float leaves it exactly where it was, on the same line. A `clear`
#     on a BLOCK child after an inline run already works, in `WalkBlockChildren`.
#   · The static position of an absolutely positioned child of an inline run is still the container's
#     content edge, not the band. §10.3.7's hypothetical box beside a float; no oracle consulted.


# ══ DELIBERATELY ABSENT — the store still cannot represent it ═══════════════════════════════════

# ⚠ THE STRUT. §10.8 begins every line box with an imaginary zero-width inline box carrying the
# block container's own font and line height. It is why an empty line is still a line tall, why a
# short image never makes a line shorter than its text would be, and why `line-height` on a
# container does anything at all. A strut is font metrics; `Vixen.Ui.Layout` has no font and no font
# size — it is geometry, and `FontRegistry` lives a layer out in `Vixen.Ui`. A line here is exactly
# as tall as the boxes on it.
#
# ⚠ This is also why the five font-relative `vertical-align` values are refused rather than
# approximated. Each is defined against the parent's strut, and rounding them to `baseline` looks
# almost right and reads as a rendering quirk. `LayoutStyleBuilder` drops the keywords; the layout
# store falls them back; `A_font_relative_vertical_align_falls_back_to_the_baseline` pins it.

the strut                         no font metrics below `Vixen.Ui`
vertical-align: middle            parent's baseline + half its x-height
vertical-align: text-top          top of the parent's strut
vertical-align: text-bottom       bottom of the parent's strut
vertical-align: sub / super       the parent's subscript / superscript offsets
vertical-align: <length> / <%>    not in the enum at all; needs `line-height` to be a percentage base

# ══ WHAT NO ORACLE COVERS, AND WHY ══════════════════════════════════════════════════════════════
#
# ⚠ MOST OF WPT'S INLINE SUITE CANNOT CROSS, AND THE REASON IS STRUCTURAL RATHER THAN LICENSING.
#
# A line box's height and baseline depend on the strut, so almost every inline test in WPT is
# implicitly a font test. `css/css-inline/` is 24 files, and it is reftests and crashtests plus one
# genuinely useful subdirectory (`baseline-source/`) whose fixtures set `font-size: 20px` and size
# their boxes in `em`. This store has no renderer and no default font, so neither half crosses.
#
# What DID cross, and it is the most valuable file found anywhere for this plan item:
#
#   wpt/css/css-flexbox/inline-flex.html    three 50×50 boxes — inline-block, inline-flex,
#                                           inline-block — with data-offset-x 0/50/100 and
#                                           data-offset-y 0 throughout, and two `flex: 1` children
#                                           at data-expected-width 25. Every box carries an explicit
#                                           size, so not one number depends on a font. This is
#                                           `Three_inline_level_boxes_share_one_line_...`.
#
# One more is reachable and is NOT yet taken:
#
#   wpt/css/css-sizing/keyword-sizes-on-inline-block.html
#                                           shrink-to-fit and the intrinsic keywords on inline-block,
#                                           in Ahem at `font: 20px/1`. ⚠ Worth knowing that this one
#                                           IS reproducible here despite being a text test: Ahem's
#                                           glyphs are 1em × 1em by specification, and this repo
#                                           already models exactly that in
#                                           `Taffy/TaffyAhemMeasure.cs`. It needs `min-content`,
#                                           `max-content` and `fit-content` as keyword sizes, which
#                                           `StyleLength` does not carry — that is the blocker, not
#                                           the font.
#
# And two sources named in doc 43 that were NOT consulted, so that nobody assumes they were:
#
#   ICU4X `components/segmenter/tests/css_line_break.rs` (72 assertions) and `css_word_break.rs`
#   (31) — the only plain-data oracle anywhere for the CSS TAILORING of line breaking
#   (`line-break: loose/normal/strict/anywhere`, `word-break: keep-all/break-all`). Unicode-3.0,
#   permissive, small enough to transcribe by hand. ⚠ Vixen's `LineBreakConformanceTests` is green
#   against UAX #14 AS WRITTEN, and browsers do not implement it as written — Parley's
#   `parley_engine/src/break_overrides.rs` documents the deltas with line-level citations into
#   Chromium, including a test named `chromium_ignores_uax_14_lb13`. Neither is relevant to THIS
#   change, because this walk breaks between atomic items and never inside text; both become
#   relevant the moment text breaking moves into the line box, which is the fragmentation work.
