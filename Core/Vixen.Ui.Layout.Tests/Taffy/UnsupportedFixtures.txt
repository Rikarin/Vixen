# Taffy fixtures that assert nothing, and the exact reason each one gives.
#
# ⚠ THIS FILE EXISTS BECAUSE A SKIP READS AS A PASS, and 408 of them did.
#
# `KnownGaps.txt`, `BlockKnownGaps.txt` and `GridKnownGaps.txt` list fixtures that LAY OUT and
# disagree with Chrome. This file lists the other kind: fixtures `TaffyStyleMap` refuses outright,
# which the three conformance suites turn into `Assert.Skip`. Those never reach the algorithm, so
# they cannot fail — and every summary anyone reads counts a skip beside a pass rather than beside a
# gap. The three suites did pin the refusal COUNT, which is why nothing could drift silently; what
# no file recorded was what the refusals were FOR. Four gap files said the corpora were nearly
# closed and none of them mentioned the 408.
#
# So: every distinct `TaffyUnsupportedException` message, per corpus, with the number of fixtures it
# accounts for. `TaffyUnsupportedCensusTests` re-derives all of it from an actual run and requires
# this file to match line for line, so a bucket cannot grow, shrink or appear without being written
# down here.
#
# Each line is `count  corpus  reason`, the reason verbatim as the exception carries it. Unlike the
# gap files, a line here covers whole fixtures rather than a base name, so the counts are already
# multiplied by the four `__{border,content}_box_{ltr,rtl}` variants.
#
#
# ══ THE SPLIT THAT MATTERS ═══════════════════════════════════════════════════════════════════════
#
# A refusal is one of two completely different things, and the number of them was the same before
# anyone looked:
#
#   · A HARNESS gap. The fixture writes a property value `TaffyStyleMap` never learned to translate,
#     and `Vixen.Ui.Layout` can express the fixture perfectly well. Costs the whole fixture — every
#     other property it sets stops being asserted too — and is worth nothing to anyone.
#   · An ENGINE gap. The store genuinely has no field for it. Belongs here with a reason, exactly
#     like a line in a gap file.
#
# Of the 408, **124 were harness and 284 were engine — 30% against 70%.** All 408 are closed.
#
#   · The harness 124: `scrollbar-width` on a box that does not scroll (104) and `writing-mode` on
#     a leaf (20).
#   · The engine 284: `scrollbar-width` on a box that does (180), the `safe` alignment families
#     (76), legacy `text-align` (16), `display: flow-root` (8) and `float` in the block corpus (4).
#
# ⚠ Those five engine numbers are the buckets AS THEY STOOD, and one of them moved before it closed:
# 4 of the 8 `flow-root` fixtures also needed a float, so when the keyword landed they became float
# refusals rather than passes, and the block corpus's float bucket went from 4 to 8. Adding the
# columns twice is how a reader ends up with 412; the movement is why they do not simply add.
#
# ⚠ And the `float` corpus's own 84 were never among the 408 at all. They were TALLIED rather than
# skipped — `TaffyPendingCorporaTests` ran every one of them and pinned `(0, 0, 84)` — so they were
# listed under FLOATS for completeness and could not be counted as skips. They converted with the
# rest, which is where 92 comes from and 408 does not grow to 492.
#
# ⚠ **NOTHING IS LISTED BELOW ANY HEADING IN THIS FILE, AND THAT IS THE STATE IT WAS WRITTEN TO WARN
# ABOUT.** A census of nothing and a census that did not run print the same page. Read the TOTAL
# section at the foot before concluding anything from the emptiness — it says what the guard was
# replaced with, and why `Assert.Empty` on this file's contents is not that guard.
#
# Closing them was worth what it was supposed to be worth. 92 of the 124 went straight to green,
# which is 92 fixtures' worth of correctness evidence that already existed and was being thrown
# away. The other 32 went red, and every one of them is a defect this corpus had been carrying
# silently — filed under new headings in `KnownGaps.txt` and `GridKnownGaps.txt`. Two of the three
# were pre-existing arithmetic that no visible fixture happened to exercise, which is the reason to
# do this rather than a cost of doing it.
#
# ⚠ **96 of the 284 ENGINE gaps have since been closed too, and they went 96 pass / 0 fail.** Safe
# alignment, legacy `text-align` and `display: flow-root` were each a real missing field rather than
# a translation the map never learned — this file said so and was right about all three — and each
# was written. Not one of the 96 that started running disagreed with Chrome, which is the opposite
# of what the harness batch did and is worth reading the right way round rather than as a victory:
# a HARNESS gap hides fixtures whose arithmetic nobody has ever checked, so it turns up defects; an
# ENGINE gap hides fixtures that were waiting on code that did not exist, so the code is written
# against them and of course they pass. Only the first kind is evidence about the algorithm.
#
# ⚠ The three buckets held 100 refusals between them and the total fell by 96, which is not an
# arithmetic slip. 4 of the 8 `display: flow-root` fixtures are `block_flow_root_contains_float`,
# which needed the keyword AND a float; they did not convert, they changed which missing feature
# they are refused for, and they are counted under FLOATS now. A bucket emptying and a fixture
# converting are two different events and this file has to be able to tell them apart.
#
# The headings for the three are kept, with their counts zeroed, under CLOSED at the foot of this
# file — a deleted heading leaves a reader unable to tell "implemented" from "never existed".
#
#
# ══ HARNESS — CLOSED ═════════════════════════════════════════════════════════════════════════════
#
# Nothing is listed under this heading, and that is its point: a harness gap is not a thing to
# record, it is a thing to fix. Both of these are in `TaffyStyleMap.Apply` and both turn on the same
# question — CAN THIS DECLARATION MOVE A BOX? — rather than on leniency.
#
# ── `scrollbar-width` on a box that does not scroll ── 104 fixtures ──
#
# The gutter is reserved by a SCROLL CONTAINER, not by the property. Chrome reserves it for
# `overflow: scroll`, and for an `overflow: auto` that actually overflows, and for nothing else. The
# corpus writes `scrollbar-width="15"` on 336 elements; 156 of them clip with `overflow: hidden`,
# where there is no scrollbar and therefore no gutter, so the declaration cannot move a box and
# accepting it is the correct translation rather than a lenience. The other 180 elements really do
# scroll, and their refusal stood until the store grew `LayoutStyle.ScrollbarWidth` — see the ENGINE
# heading below, which is now closed too. (That bucket also came to 180, in FIXTURES rather than
# elements. Coincidence — the two counts are not the same quantity, and a fixture can hold several
# of either kind.) `TaffyStyleMap` no longer asks the question at all: it applies the value on every
# box and lets `Overflow` decide, which is what the split was always about.
#   → 104 converted: 76 pass, 28 fail. The 28 are `measure_child_with_flex_shrink_hidden` and six
#     `grid_span_*_indefinite_hidden` families, and neither has anything to do with a gutter — both
#     are arithmetic that only shows on an item which OPTS OUT of a content-based automatic minimum,
#     which is what `overflow: hidden` does and what `scrollbar-width` was hiding. New headings in
#     `KnownGaps.txt` and `GridKnownGaps.txt`.
#
# ── `writing-mode: vertical-lr` on a leaf ── 20 fixtures ──
#
# ⚠ This one was a finished consumer that nothing called. `TaffyAhemMeasure` has modelled vertical
# text since it was written — it swaps which physical axis it treats as inline, and
# `TaffyFixtureRunner.Build` reads the attribute to set the flag — but the attribute loop threw
# before `SetMeasureFunction` was ever reached, so that entire branch was dead. Every one of the
# corpus's 24 `vertical-lr` elements is a childless `<text>`.
#   → 20 converted: 16 pass, 4 fail. The four that fail are `grid_relayout_vertical_text`, and they
#     are the honest limit of the argument: a leaf's own measurement is not the ONLY thing that can
#     see its axes, because its container states the constraint in flow-relative terms too. A grid
#     hands a turned item its column width as an inline constraint; Chrome hands it the row height.
#     `LayoutStyle` has no writing mode to tell the container which. Filed in `GridKnownGaps.txt`.
#
# ⚠ Nothing else qualified, and the near misses are worth naming so nobody re-litigates them.
# `align-content: safe end` is not `align-content: end` — `safe` falls back to start alignment when
# the item overflows, which is precisely what 15 of the 19 families are named for. `display:
# flow-root` is not `display: block` — the whole content of the keyword is that it establishes a
# formatting context, and `EstablishesBlockFormattingContext` read `overflow` and inline-level-ness
# and nothing else. Mapping either of those would have produced a wrong answer on the exact fixture
# that tests it, which is a hack and not a translation.
#
# ⚠ Both of those refusals stood, and both of those features are now IMPLEMENTED — which is the
# vindication of the distinction rather than a contradiction of it. The question this heading asks
# is "can the map translate this into something the store already has", and the answer for both was
# no. The answer to the different question, "should the store have it", was yes. See CLOSED.
#
#
# ══ ENGINE ═══════════════════════════════════════════════════════════════════════════════════════

# ── SCROLLBAR GUTTERS ── CLOSED, 180 ──
#
# Kept as a heading with no rows under it, because the prediction it recorded is worth checking
# against what happened. It said: additive rather than structural, one `float ScrollbarWidth` on
# `LayoutStyle`, subtracted from the content box on each axis whose `Overflow` is `Scroll`, wherever
# the padding box is resolved. **All 180 pass and not one line went into a gap file** — the only
# bucket in this census to convert whole.
#
# ⚠ Three things the prediction did not have, and each of them is a fixture rather than a nicety.
#
#   · THE AXES CROSS. `overflow-y: scroll` puts a bar down the side, and a bar down the side eats
#     WIDTH. `leaf_overflow_scrollbars_take_up_space_x_axis` scrolls across and expects the extra 15
#     points DOWN. Reading `OverflowX` for the row axis transposes every scroll container at once.
#   · THE GUTTER IS NOT A FLOOR, though padding and border are. A box may be laid out narrower than
#     its own scrollbar — the bar simply covers everything — but never narrower than its own edges.
#     `*_overflow_scrollbars_overridden_by_{size,max_size}` is a 2×4 box reserving 15 on both axes
#     and Chrome answers 2×4, so `BoundAxis`, `WithBoxSizing` and the four fit-content floors keep
#     padding and border while everything else moved to a content inset. That split is the whole
#     reason `StyleResolution` grew a second family of helpers rather than one field being added to
#     the first.
#   · IT IS INSIDE THE ABSOLUTE CONTAINING BLOCK. `inset: 0` stops at the bar, and six families
#     across three corpora measure the gutter by putting exactly such a box in a scroll container
#     and reading its size back — so the rule that looks like it belongs to `position: absolute` is
#     the one that decides whether the *scrollbar* fixtures pass. `grid_absolute_resolved_insets`
#     needed it a second time in `RecordAbsoluteGridAreas`, where an `auto` grid line resolves to
#     the same padding edge.
#
# `Overflow` still has no `Auto` member and still does not need one: the corpus writes `scroll`,
# which always reserves, and the enum's remarks argue the rest.

# ── FLOATS ── was 92, now 0 ──
#
# The last bucket, and the only one that was ever a whole layout MODE rather than a property. It said
# what it needed: "an exclusion list threaded through inline line-box construction, plus `clear`,
# plus the interaction with margin collapsing that `block_flow_root_contains_float` is about."
#   → 92 converted: 92 pass, 0 fail. `FloatSide` and `Clear` on `LayoutStyle`,
#     `LayoutTree.Floats.cs` for the exclusion list, and four sites in `LayoutTree.Block`.
#
# ⚠ **It was right about two of the three and WRONG ABOUT THE FIRST, which is the most useful thing
# this heading has to say.** There is no exclusion list in inline line-box construction, because not
# one of the 84 fixtures needs one: `grep -c '<text' Corpus/float.xml` is 0. The whole corpus is
# block-level — floats placed against each other, formatting context roots refusing to overlap them,
# clearance, and containment — and the rule everybody means by "float", a line box shortening as it
# passes one, is not tested anywhere in the 5 524. `LayoutTree.Inline` still has no idea floats
# exist. That is owed, it is filed in `InlineKnownGaps.txt`, and NOTHING IN ANY CORPUS WOULD CATCH
# IT — which is exactly the kind of claim this file was created to stop people inferring from a
# zero.
#
# ⚠ The 84 were TALLIED rather than skipped, and that distinction ends here: they are judged
# individually now by `TaffyFloatConformanceTests`, the way block and grid were when they landed. The
# 8 in `block` were real skips — `block_flow_root_avoids_sibling_float` and
# `block_flow_root_contains_float` — and they are the only part of the float work that was checked
# against a corpus written for something else. ⚠ Four of those 8 were 4 of the 8 `display: flow-root`
# refusals until the keyword landed; they did not become a pass then, they changed which of two
# missing features they name, and they became a pass now. A bucket shrinking is not the same as
# fixtures converting, and this is the one place in the file where the two came apart.


# ══ CLOSED ═══════════════════════════════════════════════════════════════════════════════════════
#
# ⚠ Kept as headings with no lines under them, because the counts are asserted and a bucket that is
# simply deleted leaves a reader unable to tell "implemented" from "never existed". Each of these
# was an ENGINE gap when it was written down, and each was written rather than translated away.
#
# ── SAFE ALIGNMENT (CSS Box Alignment §4.4) ── was 76, now 0 ──
#
# `safe` is an overflow FALLBACK, not a position: an item aligned `safe end` sits at the end edge
# until doing so would push its start edge out of the alignment container, at which point it aligns
# to start instead and overflows the other way. `Align` and `Justify` carry the position only, and
# mapping `safe end` onto `FlexEnd` would have been wrong on exactly the fixtures that test it — 15
# of the 19 families are named `_overflow`. This file said the fix was "one bit beside the position,
# and one comparison at each of the four places §4.4 is applied", and that is what it was:
# `OverflowAlignment` on `LayoutEnums`, six `*Overflow` fields on `LayoutStyle` — the four named
# plus `align-items` and `justify-items`, which the corpus does not exercise and which `align-self:
# auto` inherits from — and `LayoutTree.SafeFallback` called from six sites.
#   → 76 converted, 76 pass, 0 fail.
#
# ⚠ The four `_no_overflow` families were refused with the rest on purpose, and they were the ones
# that proved the design: they are where `safe` and unsafe agree, so a translation-time hack would
# have passed them and failed the other fifteen. They pass now for the right reason.
#
# ⚠ One asymmetry Chrome has and the spec does not obviously state, worth recording because it looks
# like a bug from either side. `absolute_safe_align_self_end_overflow` puts a 200-point out-of-flow
# child in a 100-point flex container and Chrome answers 0 — safe fired. Its twin
# `absolute_safe_justify_content_end_overflow` is the same overflow on the main axis and Chrome
# answers −100 — safe did NOT fire. The rule that reconciles them is what §4.4 measures: the
# ALIGNMENT SUBJECT. `align-self` is the child's own declaration and its subject is the child, which
# overflows. `justify-content`'s subject is the container's in-flow content, and an out-of-flow
# child is not in it — the line the static position is read off holds no items at all, so nothing
# overflows and `end` is honoured. See `LayoutTree.Absolute.LayoutAbsoluteChild`.
#
# ── LEGACY `text-align` ON A BLOCK CONTAINER ── was 16, now 0 ──
#
# `-webkit-center`, `-webkit-left` and `-webkit-right` are the legacy values that align a block
# container's BLOCK-LEVEL children, not just its inline content — the behaviour `<center>` had, kept
# alive because pages depend on it. This store had neither the property nor the step in
# `LayoutTree.Block` that would read it, and now has both: `LegacyTextAlign` and
# `LayoutTree.LegacyTextAlignOffset`, one call where a block child's physical left edge is decided.
#   → 16 converted, 16 pass, 0 fail.
#
# ⚠ The enum is `LegacyTextAlign` and not `TextAlign`, and that is not fastidiousness. Plain
# `text-align: center` centres a block container's INLINE content and leaves its block-level
# children exactly where §10.3.3 put them; only the three legacy keywords move the boxes. One field
# holding both sets would have to mean two different things, so the map refuses an unprefixed value
# rather than folding it in. `text-align` proper is still owed, still has no oracle in either
# corpus, and is still `InlineKnownGaps.txt`'s entry — which said all of this before the field
# existed and is worth reading for the arithmetic error it corrects.
#
# ⚠ `block_text_align_center_rtl` is the one that pins the keywords PHYSICAL: an RTL container puts
# its child at x=50 rather than mirroring, and `block_item_text_align_left__border_box_rtl` puts one
# at x=0 where §10.3.3 alone would have said x=100. Direction is consulted only when none of the
# three was written.
#
# ── `display: flow-root` ── was 8, now 0 ──
#
# A block container that always establishes a block formatting context, whatever its `overflow`
# says. `EstablishesBlockFormattingContext` derived the answer from `overflow` and from
# inline-level-ness, which is the complete rule for every other keyword and could not express this
# one: a `flow-root` with `overflow: visible` must still stop its children's margins escaping, and
# `block_flow_root_margin_non_collapse` is that fixture exactly. `Display` grew a `FlowRoot` member,
# `EstablishesBlockFormattingContext` grew a clause, and four `is Block or Grid`-shaped tests grew
# an arm.
#   → 4 converted, 4 pass, 0 fail. ⚠ The other 4 are `block_flow_root_contains_float`, which this
#     file predicted would need floats regardless. They are still refused, are now counted under
#     FLOATS, and are the whole of the difference between this batch's 100 and 96.
#
# ⚠ `BlockMarginsCollapsibleWithParent` deliberately did NOT grow an `or FlowRoot`, which is the one
# place the keyword reads as a missed site and is not one: a flow root's margins collapse with its
# children's in neither direction, so the literal `Display.Block` test is what enforces that.
#
#
# ── THE REFUSALS THAT NEVER FIRE ── 0 ──
#
# ⚠ Worth recording precisely because they are absent, and because they are the ones a reader
# guesses at. `TaffyStyleMap` also refuses `min-content sizing`, `fit-content()` and `fr units` from
# its `Length` helper, `clear` by name, and an area template that is not a rectangle. Not one of
# them accounts for a single fixture. `min-content`, `fit-content()` and `fr` reach the corpus only inside track lists,
# which go through `TaffyTrackListParser` and are fully supported; no fixture writes any of the
# three as a `width`, a `height`, an inset or a `flex-basis`, which is the only path into `Length`.
# `grid-template-areas` appears nowhere in the corpus at all — and is no longer refused as a whole
# property, because the store carries named areas now; only an INVALID template is. `clear` appeared 32 times, every one of
# them in the `float` corpus, whose fixtures were all refused already and recorded `float` as the
# reason — so `clear` was real debt that was invisible here because a bigger one shadowed it, which
# is a third category and the reason this heading was never just a curiosity. ⚠ It is now the ONLY
# heading in this file with rows it can still produce, since `float` and `clear` are implemented and
# what remains refused under those two names are the flow-relative keywords `inline-start` and
# `inline-end`, which need a writing mode nothing here has.
#
# They are kept as arms rather than deleted: a refreshed corpus that starts writing one has to be
# skipped rather than mis-parsed. What used to make that safe was that the census below is asserted
# bucket by bucket, so the day one of them fires it appears as a new line and the suite goes red.
# ⚠ That is no longer sufficient on its own, because an empty census cannot demonstrate that its
# instrument still works — so `TaffyUnsupportedCensusTests` now feeds the map `float: inline-start`,
# `clear: inline-end` and a non-rectangular `grid-template-areas` directly and requires all three to
# be refused — plus a VALID area template, which must NOT be, since a probe that refused everything
# would satisfy the other three.
#
#
