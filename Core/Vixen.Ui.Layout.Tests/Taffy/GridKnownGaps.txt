# Grid fixtures in Taffy's corpus that Vixen does not yet get right.
#
# Same rules as KnownGaps.txt and BlockKnownGaps.txt beside it, and the same reason for existing: a
# name here is a fixture that LAYS OUT and disagrees with Chrome, which is a different thing from
# the fixtures TaffyStyleMap or TaffyTrackListParser refuse for a property this store has no field
# for. A refusal is a skip and is counted separately; only a numeric disagreement belongs here.
#
# Names are given without the __{border,content}_box_{ltr,rtl} suffix, so one line covers up to four
# fixtures. Group them under a `# ── … ──` heading that says WHY the bucket fails and what would fix
# it — a bare list of names is a changelog, not an explanation, and the shape of this file is
# supposed to be readable as the answer to "what is missing from grid".
#
# TaffyGridConformanceTests asserts both that every failure is listed here AND that the totals are
# exactly the committed counts, so a line cannot quietly widen and a fix cannot quietly land. The
# corollary is the one rule that matters: a gap that closes comes off this file in the same commit
# as it closes, and a gap that opens does not get added without a heading explaining it.
#
# 1 896 of the 2 120 grid, blockgrid and gridflex fixtures pass, 92 fail and 132 are refused.
#
# ⚠ THE SHAPE OF THIS FILE IS THE RESULT, and it is a different shape from block's. Block landed
# with every one of its failures outside block formatting. Grid has not — but the features this
# file named as its largest have all since landed, from different branches: §11.8's baseline
# alignment, §9's containing block for an out-of-flow child, §4.4's overflow alignment, and the
# definite second pass §12 takes once an intrinsically-measured container has a width. What remains
# is arithmetic rather than whole features. Complete: placement (§8), the bulk of track sizing
# (§12), §11.8 baseline alignment, §9's containing block and §4.4 overflow alignment — every
# `grid_placement_*`, `grid_auto_flow_*`, `grid_repeat_*`, `grid_gap_*`, `grid_span_*`,
# `grid_relayout_*`, `grid_align_items_baseline_*`, `grid_align_*`, `grid_justify_*` and
# `grid_absolute_*` family is green, and so is every one of the 548 `grid_flex_track_*` fixtures,
# which are the ones that exercise §12.5 and §12.7 hardest.
#
# ⚠ <b>Two of the remaining families are not grid's, and the file should stop implying they are.</b>
# `grid_min_content_flex_column` is in the shared min-content helper, and the two
# `grid_available_space_*` fixtures are about how the ROOT node is sized — see their heading. Both
# are named here because the fixture names begin with `grid`, not because grid is where the fix is.

# ── BASELINE ALIGNMENT (§11.8) ── CLOSED ──
#
# ⚠ Sixteen fixtures, four families, and the estimate this heading used to carry — "additive: a
# per-item offset folded into MeasureGridItem's block-axis answer, plus a second pass over each
# baseline-sharing group" — turned out to be exactly right. No restructuring of §12 was needed.
# 462 → 446. See LayoutTree.Grid's ResolveBaselineShims.
#
# The shim really is an INPUT to §12 and not a nudge applied afterwards, which is what decided where
# the pass goes: after the columns, because an item's baseline depends on the inline size it was
# given, and before the rows, because §12.5 step 1 sizes a row from contributions that already
# include it. `grid_align_items_baseline_multiline` is the fixture that tells the two apart — its
# first row is 60 tall because a 20-point item sits 40 points down, and a positioning-only fix makes
# it 50 and puts the whole second row in the wrong place.
#
# ⚠ Two things learned writing it, both of which produced a green-looking pass that was wrong:
#   · The baseline probe must lay the item out with `performLayout: true`. A baseline is either the
#     box's own bottom edge or a descendant's, and the descent reads `Position[Edge.Top]`, which a
#     measurement pass never writes. This is the only place in grid sizing that asks for a layout.
#   · …and it must resolve the item's stated height first, for the reason MeasureGridItem already
#     documents: a childless box answers a max-content block request with its padding and border and
#     nothing else. A synthesised baseline IS the bottom edge, so every plain item reported a
#     baseline of zero, and the shims came out INVERTED — the tall item dropped and the short one
#     did not. It looked like a sign error and was not.
#
# What is NOT here: only items with a row span of exactly 1 join a baseline-sharing group, per
# §11.8. A spanning item is aligned as though it said `start`, and no corpus fixture disagrees.

# ── AN ITEM'S PERCENTAGE MARGINS DURING TRACK SIZING ── CLOSED, and one RTL remainder ──
#
# ⚠ Filed under baseline alignment until the baseline work closed the other four families and left
# this one standing, which is what made it legible: it was never a baseline bug. The two items are in
# one column, so each is alone in its baseline-sharing group and every shim is zero; the disagreement
# was that the first row came out 65 rather than 70.
#
# CSS Grid §9 makes an item's grid area its containing block, so a percentage margin on the item is a
# fraction of the AREA's inline size. `PlaceGridItemBoxes` got that right and said so; MeasureGridItem
# resolved the same margins against the grid's own owner width, which for a max-content container is
# NaN — so a `margin: 5%` item contributed its border box alone to the row and the row was short by
# both margins. Ten fixtures, three lines: this family's LTR pair, and both
# `grid_percent_items_width_and_margin` families, which were sitting in the cyclic-percentage bucket
# below and are not cyclic — they are this. 446 → 436.
#
# ⚠ The line stays because its two RTL variants do not. Those disagree about the *inner* child
# (`root.1.0.x`: Chrome 0, this −1), which is a half-point margin mirrored against a box that
# overflows its area and then rounded — a rounding question in `PlaceGridItemBoxes`' RTL mirror
# rather than a margin-resolution one, and nothing else in the corpus exercises it.
grid_align_items_baseline_child_margin_percent

# ── A SPANNING ITEM AGAINST AN INDEFINITE CONTAINER ── CLOSED, and two that were never this ──
#
# The heading was right about where to look and it took three separate fixes to pay out, each of
# which the previous one exposed.
#
# ⚠ <b>The intrinsic pass measures; a definite pass lays out.</b> §12.5 step 3.3 opens "if the grid
# container is being sized under a max-content constraint", and under that constraint an `auto`
# track absorbs a spanning item's max-content contribution alongside the `max-content` ones. That is
# the right answer to "how wide would this grid like to be" and the wrong answer to "how wide is
# it" — and once the first pass produces a width, the second question has a definite answer.
# `LayOutGrid` took its second pass only when a fit-content clamp had narrowed the box; it now takes
# one whenever the first pass ran under an intrinsic constraint. `max-content auto` spanned by one
# item is 60 + 20 once the 80 is known, and 40 + 40 if the max-content pass is left standing.
#
# ⚠ <b>§12.5 step 3.3 is two rounds, not one round with a widened membership.</b> Its first sentence
# spends the LIMITED max-content contribution over `auto` and `max-content` minimums; its last
# spends the full one over `max-content` minimums alone. Two memberships, two contributions, and
# they are crossed — the wider set gets the smaller number. The fused reading handed the wider set
# the larger number, so a `fit-content()` track spanned under a max-content constraint grew straight
# past its own argument. ⚠ Splitting the round alone changed NOTHING measurable, and that is the
# instructive part: the growth was arriving through the GROWTH LIMIT, not the base size, and §12.6
# then raises every base to its growth limit because free space is infinite under a max-content
# constraint. `fit-content()`'s clamp was applied for an item in exactly one track and nowhere else.
# Both halves together, and only both, are worth eight fixtures.
#
# ⚠ <b>A percentage gutter is a fraction of this grid's content box, not of its owner's.</b> CSS Box
# Alignment §8, and `LayOutGrid` was passing `ownerWidth`. The definite case is simply wrong and now
# resolves up front; the indefinite case cannot resolve until the max-content pass has produced a
# number, and then re-sizes the tracks around the gutter without re-measuring the box — so
# `column-gap: 20%` on a grid that measures 100 wide is 20 points of gutter and the tracks overflow
# to 120, which is what Chrome draws.
#
# Ten families here, plus six from the cyclic-percentage bucket, three of the `_with_padding_border`
# family and `grid_overflow_rows` — 76 fixtures for a heading that claimed 48.

# ── HOW THE ROOT NODE IS SIZED, WHICH IS NOT A GRID QUESTION ──
#
# ⚠ These two sat under the spanning-item heading above and are not that: NEITHER HAS A SPANNING
# ITEM. Both are `auto auto` with one text per track, and in both the tracks come out exactly right
# — 80 + 80 in the first, 40 + 40 in the second. The only number that disagrees is the container's
# own width, and it disagrees with the available space rather than with the content.
#
# `CalculateLayout` sizes a root with no stated width as StretchFit whenever it is handed a definite
# owner size, which is Yoga's rule and what the 534 Yoga fixtures are written against. Chrome
# shrink-to-fits it: fit-content, floored at min-content. So a grid whose max-content size is 160 in
# a 400-point viewport is 160 and not 400, and one whose min-content size is 80 in a 60-point
# viewport is 80 and not 60. The two fixtures are the two sides of that one clamp, and no
# grid-side change can satisfy both — the first needs the box to shrink below the available space
# and the second needs it to grow past it.
#
# Left here rather than deleted because the names begin with `grid`, but the fix is in
# `LayoutTree.Layout`'s root entry and it is shared with block and flex. Whoever takes it should
# expect to re-measure all four corpora, not this one.
#
# ── ⚠ THE CONFLICT THIS HEADING NAMES IS NOT THE CONFLICT. MEASURED ON agent/flex-basis-and-root. ──
#
# The premise was "that is Yoga's rule and what the 534 Yoga fixtures are written against", i.e. that
# satisfying Chrome here costs Yoga's corpus. IT DOES NOT. Switching the root's indefinite-width
# branch from `SizingMode.StretchFit` to `SizingMode.FitContent` — one line in `CalculateLayout` —
# leaves **all 534 Yoga fixtures green**, leaves flex at 2 190 / 66 / 152 and block at 788 / 0 / 124
# untouched, and moves grid 1 896 → 1 898. Not one fixture in any of the four corpora moves the wrong
# way. Only 20 grid fixtures and no flex or block fixture give the root a definite viewport width at
# all, which is why the corpora have so little to say about it.
#
# ⚠ WHAT IT COSTS IS VIXEN'S OWN SURFACE CONTRACT, and that is a product decision rather than a layout
# one. Six tests in `Core/Vixen.Ui.Tests` fail, headed by
# `UiDocumentTests.The_root_is_laid_out_against_the_surface_rather_than_against_nothing`: `UiDocument`
# calls `CalculateLayout(surface.Root, surface.Width, surface.Height, …)`, and a surface root with no
# stated width would stop filling its window and shrink to its content.
#
# ⚠ **ANSWERED 2026-08-09: a Vixen surface root FILLS ITS WINDOW, and these two fixtures stay here
# permanently as a deliberate divergence rather than as work.** Jiu decided it, and the reasoning is
# stronger than the preference: on the web the root element with `width: auto` is a block-level box
# whose containing block is the initial containing block, and it FILLS it. Chrome's shrink-to-fit in
# these fixtures is not a rule about document roots at all — it is what a grid CONTAINER does when
# handed definite available space. Taffy gives the root a definite viewport width as a harness
# convention for measuring, which is why only 20 grid fixtures do it and no flex or block fixture
# does. The two oracles are not disagreeing about roots; they are disagreeing about what the
# harness's outer box means.
#
# So do not "fix" these by switching the root's sizing mode. If a future change makes them pass, check
# first that `UiDocumentTests.The_root_is_laid_out_against_the_surface_rather_than_against_nothing`
# and its five siblings still pass too — if they do not, the change took a window's width away from a
# window.
#
# ⚠ AND THE ONE LINE IS NOT THE WHOLE FIX EVEN IF THE ANSWER IS "CHROME". It closes 2 of these 8
# fixtures, and the other 6 need two rules this heading never named:
#   · `_smaller_than_min_content` stays at 60. `SizingMode.FitContent` caps at the available space
#     and does not FLOOR at min-content, which is the other half of CSS Sizing §5.1's fit-content.
#   · Both RTL halves then fail on placement instead of size: a shrink-to-fit root in a 400pt owner
#     box is expected at x=240, and the root entry puts every root at x=0. A root narrower than its
#     owner has a leftover to distribute, and in RTL it goes on the left.
grid_available_space_greater_than_max_content
grid_available_space_smaller_than_min_content

# ── ALIGNMENT OF AN ITEM THAT IS BIGGER THAN ITS AREA (§4.4) ── CLOSED ──
#
# ⚠ The heading this bucket carried was half right, and the wrong half was the confident half. It
# said `AlignInArea`'s clamp on negative free space was the bug and `PositionTracks`' identical
# clamp was correct — the tracks falling back to start, the item overflowing. In fact BOTH clamps
# were wrong, and the bucket's own contents said so: `grid_unsafe_justify_content_end_overflow` is a
# CONTENT alignment fixture, so it goes through `PositionTracks`, and it expects x = −20. So do the
# four `_negative_space_gap` families, which are `align-content` and `justify-content` throughout.
#
# CSS Box Alignment §4.4 gives each alignment an overflow behaviour, and the default is `unsafe`:
# `center` and `end` overflow in the direction they align rather than falling back to start. `safe`
# is the keyword that asks for the fallback — and `TaffyStyleMap` REFUSES `safe X` outright while
# stripping `unsafe X`, on the stated grounds that unsafe is what every keyword in this store means.
# Both clamps contradicted the store's own vocabulary, and the two-line fix was to delete them.
#
# ⚠ Deleting `PositionTracks`' clamp outright cost four families, and that regression is what named
# the real criterion. §4.2's DISTRIBUTED alignments each declare a fallback for when there is
# nothing left to distribute: `space-between` becomes `start`, and `space-around` and `space-evenly`
# become `safe center` — and the `safe` there is load-bearing, because a bare `center` would
# overflow by half. All three arrive at start. Mapping the latter two to a plain `Center` put every
# track half the overflow to the left, which `grid_justify_content_space_around_negative_space_gap`
# and its `space_evenly` twin caught. So: positional alignments honour negative free space,
# distributed ones step aside for it.
#
# Twelve families, 48 fixtures, and two more that were misfiled under cyclic percentages below.

# ── ASPECT RATIO AGAINST A GRID AREA, AND AGAINST A FULL SET OF INSETS ──
#
# ⚠ CLOSED, together with the sixteen-family flex bucket of the same name and the five-family block
# one — which is what the note below predicted, and the prediction is the reason all three were done
# at once rather than three times. 340 → 324 here. The full write-up is in KnownGaps.txt; what grid
# needed on top of the shared rules is one sentence:
#
#   A GRID ITEM WITH AN ASPECT RATIO IS NOT STRETCHED DOWN THE BLOCK AXIS. CSS Box Alignment §6.2's
#   `normal` fills the area only where the item has nothing else to say, and CSS Sizing §4.1's
#   definite-inline-implies-definite-block is something else to say. `grid_aspect_ratio_fill_child_height`
#   is the one-line demonstration: `width: 50px; aspect-ratio: 2` in a 100×100 grid is 50×25, and
#   stretching gave it the area's 100. The inline axis is clamped by the ratio-merged bounds FIRST
#   and the block axis derived from the clamped value, which is the same order LayoutTree.Absolute
#   uses and the reason `grid_aspect_ratio_fill_child_max_width` comes out 40×20 rather than 100×20.
#
# ⚠ And grid differs from flex here in a way worth keeping: a bound carried across the ratio DOES
# reach a grid item's stretched inline axis, and does NOT reach a flex item's stretched cross axis.
# `grid_aspect_ratio_fill_child_max_width` and `aspect_ratio_flex_column_stretch_fill_max_width` are
# both `max-height: 20px; aspect-ratio: 2` on a box whose parent fills its inline axis, and Chrome
# answers 40 wide for the grid item and 100 wide for the flex one. Flexbox §9.4 stretches an `auto`
# cross size unconditionally; Box Alignment's `normal` does not. `IsFlexItem` versus
# `IsFlexOrGridItem` in LayoutTree.Helpers is that difference and nothing else.
#
# ⚠ The last of the four was the §9 bucket's one survivor, and it was here rather than there because
# §9 was not what it was about. Its grid area is the whole padding box — the child names no line —
# so the containing block was already right and the box was still wrong: with `aspect-ratio: 3` and
# all four insets at 5% of a 400×300 box, Chrome reads the inline axis off the insets (360) and then
# lets the RATIO decide the height (120), ignoring `bottom` as over-constrained. This store solved
# both axes from their insets and answered 360×270, exactly as it did for the identically-named
# `absolute_aspect_ratio_*` families under flex and block. One rule in LayoutTree.Absolute for all
# three absolute paths, as predicted.
