#
# ⚠ Sixteen fixtures, four families, and the estimate this heading used to carry — "additive: a
# per-item offset folded into MeasureGridItem's block-axis answer, plus a second pass over each

# 462 → 446. See LayoutTree.Grid's ResolveBaselineShims.

# The shim really is an INPUT to §12 and not a nudge applied afterwards, which is what decided where
# the pass goes: after the columns, because an item's baseline depends on the inline size it was
# given, and before the rows, because §12.5 step 1 sizes a row from contributions that already
# include it. `grid_align_items_baseline_multiline` is the fixture that tells the two apart — its

# ── A SPANNING ITEM AGAINST AN INDEFINITE CONTAINER ── CLOSED, and two that were never this ──
#
# The heading was right about where to look and it took three separate fixes to pay out, each of
# which the previous one exposed.
#
# ⚠ <b>The intrinsic pass measures; a definite pass lays out.</b> §12.5 step 3.3 opens "if the grid
# container is being sized under a max-content constraint", and under that constraint an `auto`
# track absorbs a spanning item's max-content contribution alongside the `max-content` ones. That is
# the right answer to "how wide would this grid like to be" and the wrong answer to "how wide is
# it" — and once the first pass produces a width, the second question has a definite answer.
# `LayOutGrid` took its second pass only when a fit-content clamp had narrowed the box; it now takes
# one whenever the first pass ran under an intrinsic constraint. `max-content auto` spanned by one
# item is 60 + 20 once the 80 is known, and 40 + 40 if the max-content pass is left standing.
#
# ⚠ <b>§12.5 step 3.3 is two rounds, not one round with a widened membership.</b> Its first sentence
# spends the LIMITED max-content contribution over `auto` and `max-content` minimums; its last
# spends the full one over `max-content` minimums alone. Two memberships, two contributions, and
# they are crossed — the wider set gets the smaller number. The fused reading handed the wider set
# the larger number, so a `fit-content()` track spanned under a max-content constraint grew straight
# past its own argument. ⚠ Splitting the round alone changed NOTHING measurable, and that is the
# instructive part: the growth was arriving through the GROWTH LIMIT, not the base size, and §12.6
# then raises every base to its growth limit because free space is infinite under a max-content
# constraint. `fit-content()`'s clamp was applied for an item in exactly one track and nowhere else.
# Both halves together, and only both, are worth eight fixtures.
#
# ⚠ <b>A percentage gutter is a fraction of this grid's content box, not of its owner's.</b> CSS Box
# Alignment §8, and `LayOutGrid` was passing `ownerWidth`. The definite case is simply wrong and now
# resolves up front; the indefinite case cannot resolve until the max-content pass has produced a
# number, and then re-sizes the tracks around the gutter without re-measuring the box — so
# `column-gap: 20%` on a grid that measures 100 wide is 20 points of gutter and the tracks overflow
# to 120, which is what Chrome draws.
#
# Ten families here, plus six from the cyclic-percentage bucket, three of the `_with_padding_border`
# family and `grid_overflow_rows` — 76 fixtures for a heading that claimed 48.

# ── HOW THE ROOT NODE IS SIZED, WHICH IS NOT A GRID QUESTION ──
#
# ⚠ These two sat under the spanning-item heading above and are not that: NEITHER HAS A SPANNING
# ITEM. Both are `auto auto` with one text per track, and in both the tracks come out exactly right
# — 80 + 80 in the first, 40 + 40 in the second. The only number that disagrees is the container's
# own width, and it disagrees with the available space rather than with the content.
#
# `CalculateLayout` sizes a root with no stated width as StretchFit whenever it is handed a definite
# owner size, which is Yoga's rule and what the 534 Yoga fixtures are written against. Chrome
# shrink-to-fits it: fit-content, floored at min-content. So a grid whose max-content size is 160 in
# a 400-point viewport is 160 and not 400, and one whose min-content size is 80 in a 60-point
# viewport is 80 and not 60. The two fixtures are the two sides of that one clamp, and no
# grid-side change can satisfy both — the first needs the box to shrink below the available space
# and the second needs it to grow past it.
#
# Left here rather than deleted because the names begin with `grid`, but the fix is in
# `LayoutTree.Layout`'s root entry and it is shared with block and flex. Whoever takes it should
# expect to re-measure all four corpora, not this one.
#
# ── ⚠ THE CONFLICT THIS HEADING NAMES IS NOT THE CONFLICT. MEASURED ON agent/flex-basis-and-root. ──
#
# The premise was "that is Yoga's rule and what the 534 Yoga fixtures are written against", i.e. that
# satisfying Chrome here costs Yoga's corpus. IT DOES NOT. Switching the root's indefinite-width
# branch from `SizingMode.StretchFit` to `SizingMode.FitContent` — one line in `CalculateLayout` —
# leaves **all 534 Yoga fixtures green**, leaves flex at 2 190 / 66 / 152 and block at 788 / 0 / 124
# untouched, and moves grid 1 896 → 1 898. Not one fixture in any of the four corpora moves the wrong
# way. Only 20 grid fixtures and no flex or block fixture give the root a definite viewport width at
# all, which is why the corpora have so little to say about it.
#
# ⚠ WHAT IT COSTS IS VIXEN'S OWN SURFACE CONTRACT, and that is a product decision rather than a layout
# one. Six tests in `Core/Vixen.Ui.Tests` fail, headed by
# `UiDocumentTests.The_root_is_laid_out_against_the_surface_rather_than_against_nothing`: `UiDocument`
# calls `CalculateLayout(surface.Root, surface.Width, surface.Height, …)`, and a surface root with no
# stated width would stop filling its window and shrink to its content.
#
# ⚠ **ANSWERED 2026-08-09: a Vixen surface root FILLS ITS WINDOW, and these two fixtures stay here
# permanently as a deliberate divergence rather than as work.** Jiu decided it, and the reasoning is
# stronger than the preference: on the web the root element with `width: auto` is a block-level box
# whose containing block is the initial containing block, and it FILLS it. Chrome's shrink-to-fit in
# these fixtures is not a rule about document roots at all — it is what a grid CONTAINER does when
# handed definite available space. Taffy gives the root a definite viewport width as a harness
# convention for measuring, which is why only 20 grid fixtures do it and no flex or block fixture
# does. The two oracles are not disagreeing about roots; they are disagreeing about what the
# harness's outer box means.
#
# So do not "fix" these by switching the root's sizing mode. If a future change makes them pass, check
# first that `UiDocumentTests.The_root_is_laid_out_against_the_surface_rather_than_against_nothing`
# and its five siblings still pass too — if they do not, the change took a window's width away from a
# window.
#
# ⚠ AND THE ONE LINE IS NOT THE WHOLE FIX EVEN IF THE ANSWER IS "CHROME". It closes 2 of these 8
# fixtures, and the other 6 need two rules this heading never named:
#   · `_smaller_than_min_content` stays at 60. `SizingMode.FitContent` caps at the available space
#     and does not FLOOR at min-content, which is the other half of CSS Sizing §5.1's fit-content.
#   · Both RTL halves then fail on placement instead of size: a shrink-to-fit root in a 400pt owner
#     box is expected at x=240, and the root entry puts every root at x=0. A root narrower than its
#     owner has a leftover to distribute, and in RTL it goes on the left.
grid_available_space_greater_than_max_content
grid_available_space_smaller_than_min_content

# ── ALIGNMENT OF AN ITEM THAT IS BIGGER THAN ITS AREA (§4.4) ── CLOSED ──
#
# ⚠ The heading this bucket carried was half right, and the wrong half was the confident half. It

# ── A GRID THIS STORE WILL NOT ALLOCATE ── CLOSED, and every claim this heading made was wrong ──
#
# ⚠ <b>TWO OF THE SEVEN HAD NOTHING TO DO WITH ANY CAP, and the reason they were filed here is a
# lesson about this corpus: a fixture with a big number in it reads as a big-number fixture.</b>
# `grid_placement_auto_negative` and `grid_overlarge_auto_flow_column_large_negative_row_start` both
# disagreed about WHICH CELL one auto-placed item took, and the rule is §8.5 step 4's opening

# `PlaceGridItems` shared a cursor. Eight fixtures, four lines, and the `-19553` in the second
# fixture's markup was never the point.
#
# ⚠ <b>AND THE HEADING'S PREMISE — "Chrome's cap and ours are different numbers" — IS WRONG FOR AT
# LEAST TWO OF THE FIVE THAT ARE LEFT. Chrome is not capping. It is computing.</b>
#   · `grid_overlarge_extreme_line_numbers` places two items at ±32 767 and expects a 40x40 grid with
#     one item in each of two rows and two columns. That is not a clamped answer, it is the EXACT
#     one: every track between them is an empty `auto` track, an empty `auto` track is zero wide, and
#     ~65 000 zeroes sum to zero. Chrome's implicit grid really is that big and costs nothing because
#     nothing in it is.
#   · `grid_overlarge_negative_line_with_explicit_tracks` is the same story with 9 000 explicit 0px
#     columns and a line at −19 005: one 20-point implicit column, ten thousand zeroes, a 20-point
#     item at x=20. Exact again.
# `LayoutLimits.MaximumGridTracks` truncates at 10 000 and pulls both items into the same track,
# which is why the widths come back halved rather than merely rounded.
#
# ⚠ <b>AND THEN THE CONCLUSION THIS HEADING DREW FROM ITS OWN CORRECT DIAGNOSIS WAS WRONG, WHICH IS
# THE MORE USEFUL HALF.</b> It read: "the work here is NOT reverse-engineering a cap. It is
# representing a sparse implicit grid — materialising the occupied tracks and the runs between them
# rather than one entry per line… That is a change to `TrackArena` and `PlaceGridItems`, not to a
# constant." It was measured. **It is a constant.** Raising
# `LayoutLimits.MaximumGridTracks` from 10 000 to 65 535 closes all five of the fixtures that were
# listed here, all twenty of their variants, with no regression in any of the four corpora and no
# measurable change in how long the 2 120 fixtures take to run. Nothing sparse was written.
#
# ⚠ The reason the diagnosis was right and the conclusion was not is that DENSE IS NOT THE PROBLEM;
# SATURATION IS. `PlaceGridItems` clamps an over-large grid with
# `item.ColumnStart = int.Clamp(item.ColumnStart, 0, columns - 1)`, so two items far apart both land
# on the LAST track and merge into one cell. That is what halved the widths, and it is a property of
# the clamp rather than of the representation: a grid big enough that the two items do not collide
# gives Chrome's answer through the arithmetic already in §12, exactly as the heading said it would.
# 65 535 is big enough because the widest grid a document can NAME is the i16 line range the corpus
# writes — ±32 767, which Taffy's own fixture names call `over_u16`.
#
# ⚠ AND THE JUSTIFICATION THE CONSTANT USED TO CARRY WAS FALSE, which is why nobody had questioned
# its value. `LayoutLimits.MaximumGridTracks` said Chrome's cap "is what the corpus recorded:
# `repeat(10000, 0px)`, `repeat(32768, …)` and `repeat(40000, 10px 10px)` are all in there
# specifically to pin the clamped answer". Not one of those three pins anything: every track in them
# is zero-sized or the item under test is in the first track, so all three give the same answer with
# a cap of 10 000, of 65 535 and of none at all. They were never evidence for the number.
#
# ⚠ WHAT IS STILL TRUE is that a cap is a memory bound and this one costs more than it did: a
# `GridTrackState` is ~48 bytes, so a document that really does write `grid-column-start: 32767` now
# makes one axis's arena ~3 MB instead of ~0.5 MB. Bounded either way, paid only by a document that
# asks, and the arena is a stack that hands the run back. The remaining honest work — and it is not
# owed by any fixture in this corpus — is to make the clamp COLLAPSE the empty runs between occupied
# tracks instead of saturating positions onto the last one, after which the ceiling stops deciding
# whether two items share a cell and becomes a pure allocation bound.
#
# ⚠ <b>THERE ARE TWO SATURATING CLAMPS AND THE ONE NAMED ABOVE IS NOT THE ONE THAT BINDS.</b>
# `int.Clamp(item.ColumnStart, 0, columns - 1)` runs at the END of `PlaceGridItems`, after the
# extents are known. `ClampPlacement` runs at the START, before any extent exists, and it saturates
# `placement.Start` at `MaximumGridTracks` on its own — so two items whose authored lines are BOTH
# past the ceiling have already been merged into one cell before the later clamp is reached. Either
# one alone is enough to merge them, which means a change to only the clamp this note names cannot
# separate anything: both have to become the same collapse.
#
# ⚠ The threshold is "both past the ceiling", not "far apart", and that is worth writing down
# because it is what a first attempt at a witness gets wrong. Measured on a hand-built max-content
# grid holding two 50-point items on two named lines, nothing else:
#
#     lines     3 and     5 → grid 100 wide, items at x=0 and x=50
#     lines 65534 and 65536 → grid 100 wide, items at x=0 and x=50   ← one is inside the ceiling
#     lines 70000 and 80000 → grid  50 wide, BOTH items at x=0       ← one cell, silently
#
# The middle row is the instrument check: a witness that puts one item at line 1 can never fail,
# because the near item survives the clamp and the two never collide. And the symptom needs items
# with a SIZE — a probe built from empty boxes reports x=300 for both whether they share a track or
# occupy two zero-width ones, so it cannot tell the defect from the fix.

# ── SINGLETONS, EACH ITS OWN STORY ── three of four closed ──
#
# ⚠ <b>`grid_auto_columns` / `grid_auto_rows` WERE A RULE, and this heading said they were not.</b>
# It read "Chrome appears to phase it differently… worth a fixture-level look, not a rule", and the
# rule is one sentence of §7.5: "the first implicit grid track AFTER the explicit grid receives the
# FIRST specified size, and so on forwards; and the LAST implicit grid track BEFORE the explicit grid
# receives the LAST specified size, and so on backwards." The cycle runs outwards from the explicit
# grid in both directions and the two directions do not share a phase, so `grid-auto-rows:
# 10px 20px 30px` gives the row immediately above the explicit grid 30 and not 10. `BuildGridTracks`
# numbered every implicit track forwards from the start of the implicit grid — and carried a comment
# asserting that as the spec, which is why nobody re-read it. `ImplicitTrackSize`'s flooring modulo
# was already written for the negative ordinal it never received.
#
# ⚠ <b>`grid_min_content_flex_column` closed in the shared helper, as this heading predicted, but
# not at the line it predicted.</b> The diagnosis was "ComputeMinContentSizeUncached has no grid
# branch — it sums children along FlexDirection as though every container were a flex one". That
# defect is real and is written up in KnownGaps.txt; it is not what this fixture failed on. The grid
# reported its width correctly. What was wrong was the BLOCK axis of the leaf probe one level down:
# it measured a text with the width undefined, so a two-line item reported one line's height, §4.5's
# floor for a column flex item was a third of what it should be, and three 20-point texts squeezed
# into a 40-point row instead of overflowing it. There is no min-content height of a paragraph on its
# own — only the height it takes at the inline size it has.
#   ⚠ That change costs `aspect_ratio_flex_column_stretch_fill_max_height` on its own, and the
#   regression is the other half of the rule: §4.5's CONTENT SIZE SUGGESTION is clamped through the
#   ratio by the cross MIN AND MAX, which is a different clamp from the transferred size suggestion
#   beside it. Both halves are +4 here and +4 in flex; the first half alone is +4 and −4.
#
# ⚠ `grid_overflow_rows` was here as "a scroll container's fit-content height, one level down from
#   the rule LayoutTree.Block already implements for itself", and it was not that at all — it closed
#   with the definite second pass and never involved a scroll container's height. A singleton is the
#   easiest kind of entry to guess wrong about, because nothing else in the bucket contradicts it.
#   Three of the four originals have now been guessed wrong about, which is a rate worth quoting.
#
# ⚠ `chrome_issue_325928327` is the one left, and it is at least classified now. A `height: 100%`
#   item wrapping a `height: 100%; aspect-ratio: 1` child, in a grid whose height is a stated 40px:
#   Chrome reads the item's inline max-content contribution as 40, this store as 0. The column pass
#   measures items with the block axis indefinite — deliberately, per CSS Sizing §5.2.1 — so the
#   inner percentage resolves to nothing and the ratio has no inline size to derive. Chrome resolves
#   it because the CONTAINER's block size is definite even though the AREA's is not yet, which is a
#   distinction §12 does not currently carry into the inline pass. Genuinely cyclic; the fixture is
#   named after Chrome's own bug tracker, which is its own comment on how settled the answer is.
chrome_issue_325928327


# ── §5.2.2's SCROLLABLE-OVERFLOW EXCLUSION IS APPLIED TO THE MIN-CONTENT CONTRIBUTION, NOT ONLY TO
#    THE AUTOMATIC MINIMUM ── six families, 24 fixtures ──
#
# ⚠ <b>NEWLY VISIBLE, NOT NEWLY BROKEN, AND THE MECHANISM BY WHICH IT WAS INVISIBLE IS THE POINT OF
# THE WHOLE HEADING.</b> Every fixture here writes `scrollbar-width="15"` beside `overflow: hidden`.
# The gutter is reserved by a scroll container and `hidden` is not one, so the declaration could
# never have moved a box — but TaffyStyleMap refused it, and refusing one inert property threw away
# the fixture's assertions about a completely different rule. These 24 are what was underneath. See
# UnsupportedFixtures.txt.
#
# `grid_span_2_min_content_auto_indefinite_hidden` is the whole story in six boxes. Two columns,
# `min-content auto`, spanned by a text of two four-character words. Chrome: 40 and 40. Vixen: 0 and
# 80. The same fixture WITHOUT the `overflow` — `grid_span_2_min_content_auto_indefinite`, four
# lines different — is green at Chrome's 20 and 60, so §12.5's spanning distribution is right and
# the disagreement is one input to it.
#
# Work the two by hand and they separate cleanly. Visible: the item's minimum contribution is 40, so
# round 1 (intrinsic minima, both tracks) splits it 20/20 and round 3 gives the `auto` track the
# remaining 40. Hidden: §6.6 zeroes the automatic minimum — correctly, that is what a scroll
# container means — so round 1 distributes nothing, round 2 (§12.5 step 3.2, `min-content` and
# `max-content` MINIMA only) should hand the first track the item's MIN-CONTENT CONTRIBUTION of 40,
# and round 3 gives the other 40 to `auto`. Chrome's 40/40 is exactly that. Vixen's round 2
# distributes zero, so everything lands in the `auto` track.
#
# ⚠ It distributes zero because the item's min-content contribution is ALSO zero, from
# `ComputeMinContentSizeUncached`'s first clause: a box whose axis is not `overflow: visible`
# returns its own padding and border and nothing else. That clause is CSS Sizing §5.2.2 as applied
# to the AUTOMATIC MINIMUM SIZE — `min-width: auto` on a scroll container is 0 — and
# `AutomaticMinimumIsZero` in LayoutTree.Grid already implements it separately and correctly. Applied to the
# min-content SIZE as well, it is applied twice, and the second application is the one that steals
# the `min-content` track's share. A scroll container's min-content size is still its contents' —
# which is why `width: min-content` on an `overflow: auto` div is not zero in any browser.
#
# ⚠ AND THE CLAUSE'S OWN COMMENT SAYS IT HAS NO WITNESS: "Nothing in either corpus asks for this,
# and the editor is what found it." That was true when it was written and is now false, and it was
# only ever true because the fixtures that ask were refused. The editor case it was written for —
# the docking chain, every box `overflow: hidden`, a shell 2 385 points wide inside a 1 100-point
# window — is real and must keep working, so the fix is NOT to delete the clause. It is to give the
# two questions two answers: the automatic minimum keeps the zero, the min-content contribution does
# not. `MinContentContribution` is already the seam between them.

# ── A TURNED WRITING MODE IS THE CONTAINER'S BUSINESS TOO ── one family ──
#
# ⚠ Also newly visible, and this one is the honest cost of the argument that made it visible.
# `writing-mode: vertical-lr` is now accepted on a childless box, because the only thing that could
# see a leaf's turned axes was thought to be its own intrinsic measurement — and `TaffyAhemMeasure`
# has modelled that since the day it was written, swapping which physical axis it treats as inline.
# Sixteen of the corpus's twenty vertical-text fixtures agree, and had been asserting nothing.
#
# These four are the counterexample, and they are a fair one. `grid_relayout_vertical_text` puts a
# turned text in a `min-content` column of a grid whose row is a stated 40px. Chrome sizes the item
# against the ROW — the row is the item's inline axis once it is turned, 40 points is four Ahem
# characters, two two-character words per line, seven words, four lines, so the column is 40 wide.
# This store hands it the COLUMN as the inline constraint, because §12 asks for a width and a height
# and `LayoutStyle` has no writing mode to tell it which of those is the item's inline axis. 40x60
# against 20x70.
#
# So the refusal was hiding sixteen green fixtures and four red ones, and the four are worth more
# than the sixteen: they name precisely what a writing mode would have to be for, which is not text
# measurement at all. It is which axis a container states a constraint in. That is a field on
# `LayoutStyle` and a swap at every point where §12, §9 and block layout convert between physical
# and flow-relative — a real feature, and the first fixture in this corpus to ask for it.
