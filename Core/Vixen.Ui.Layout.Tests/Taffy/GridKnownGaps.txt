# Grid fixtures in Taffy's corpus that Vixen does not yet get right.
#
# Same rules as KnownGaps.txt and BlockKnownGaps.txt beside it, and the same reason for existing: a
# name here is a fixture that LAYS OUT and disagrees with Chrome, which is a different thing from
# the fixtures TaffyStyleMap or TaffyTrackListParser refuse for a property this store has no field
# for. A refusal is a skip and is counted separately; only a numeric disagreement belongs here.
#
# Names are given without the __{border,content}_box_{ltr,rtl} suffix, so one line covers up to four
# fixtures. Group them under a `# ── … ──` heading that says WHY the bucket fails and what would fix
# it — a bare list of names is a changelog, not an explanation, and the shape of this file is
# supposed to be readable as the answer to "what is missing from grid".
#
# TaffyGridConformanceTests asserts both that every failure is listed here AND that the totals are
# exactly the committed counts, so a line cannot quietly widen and a fix cannot quietly land. The
# corollary is the one rule that matters: a gap that closes comes off this file in the same commit
# as it closes, and a gap that opens does not get added without a heading explaining it.
#
# 1 768 of the 2 120 grid, blockgrid and gridflex fixtures pass, 220 fail and 132 are refused.
#
# ⚠ THE SHAPE OF THIS FILE IS THE RESULT, and it is a different shape from block's. Block landed
# with every one of its failures outside block formatting. Grid has not — but the two features this
# file named as its largest have both since landed, in the same afternoon and from different
# branches: §11.8's baseline alignment and §9's containing block for an out-of-flow child. What
# remains is arithmetic rather than whole features. Complete: placement (§8), the bulk of track
# sizing (§12), §11.8 baseline alignment and §9's containing block — every `grid_placement_*`,
# `grid_auto_flow_*`, `grid_repeat_*`, `grid_gap_*`, `grid_span_*` non-indefinite,
# `grid_relayout_*`, `grid_align_items_baseline_*` and `grid_absolute_*` family is green, and so is
# every one of the 548 `grid_flex_track_*` fixtures, which are the ones that exercise §12.5 and
# §12.7 hardest.

# ── BASELINE ALIGNMENT (§11.8) ── CLOSED ──
#
# ⚠ Sixteen fixtures, four families, and the estimate this heading used to carry — "additive: a
# per-item offset folded into MeasureGridItem's block-axis answer, plus a second pass over each
# baseline-sharing group" — turned out to be exactly right. No restructuring of §12 was needed.
# 462 → 446. See LayoutTree.Grid's ResolveBaselineShims.
#
# The shim really is an INPUT to §12 and not a nudge applied afterwards, which is what decided where
# the pass goes: after the columns, because an item's baseline depends on the inline size it was
# given, and before the rows, because §12.5 step 1 sizes a row from contributions that already
# include it. `grid_align_items_baseline_multiline` is the fixture that tells the two apart — its
# first row is 60 tall because a 20-point item sits 40 points down, and a positioning-only fix makes
# it 50 and puts the whole second row in the wrong place.
#
# ⚠ Two things learned writing it, both of which produced a green-looking pass that was wrong:
#   · The baseline probe must lay the item out with `performLayout: true`. A baseline is either the
#     box's own bottom edge or a descendant's, and the descent reads `Position[Edge.Top]`, which a
#     measurement pass never writes. This is the only place in grid sizing that asks for a layout.
#   · …and it must resolve the item's stated height first, for the reason MeasureGridItem already
#     documents: a childless box answers a max-content block request with its padding and border and
#     nothing else. A synthesised baseline IS the bottom edge, so every plain item reported a
#     baseline of zero, and the shims came out INVERTED — the tall item dropped and the short one
#     did not. It looked like a sign error and was not.
#
# What is NOT here: only items with a row span of exactly 1 join a baseline-sharing group, per
# §11.8. A spanning item is aligned as though it said `start`, and no corpus fixture disagrees.

# ── AN ITEM'S PERCENTAGE MARGINS DURING TRACK SIZING ── CLOSED, and one RTL remainder ──
#
# ⚠ Filed under baseline alignment until the baseline work closed the other four families and left
# this one standing, which is what made it legible: it was never a baseline bug. The two items are in
# one column, so each is alone in its baseline-sharing group and every shim is zero; the disagreement
# was that the first row came out 65 rather than 70.
#
# CSS Grid §9 makes an item's grid area its containing block, so a percentage margin on the item is a
# fraction of the AREA's inline size. `PlaceGridItemBoxes` got that right and said so; MeasureGridItem
# resolved the same margins against the grid's own owner width, which for a max-content container is
# NaN — so a `margin: 5%` item contributed its border box alone to the row and the row was short by
# both margins. Ten fixtures, three lines: this family's LTR pair, and both
# `grid_percent_items_width_and_margin` families, which were sitting in the cyclic-percentage bucket
# below and are not cyclic — they are this. 446 → 436.
#
# ⚠ The line stays because its two RTL variants do not. Those disagree about the *inner* child
# (`root.1.0.x`: Chrome 0, this −1), which is a half-point margin mirrored against a box that
# overflows its area and then rounded — a rounding question in `PlaceGridItemBoxes`' RTL mirror
# rather than a margin-resolution one, and nothing else in the corpus exercises it.
grid_align_items_baseline_child_margin_percent

# ── ASPECT RATIO AGAINST A GRID AREA, AND AGAINST A FULL SET OF INSETS ──
#
# ⚠ CLOSED, together with the sixteen-family flex bucket of the same name and the five-family block
# one — which is what the note below predicted, and the prediction is the reason all three were done
# at once rather than three times. 340 → 324 here. The full write-up is in KnownGaps.txt; what grid
# needed on top of the shared rules is one sentence:
#
#   A GRID ITEM WITH AN ASPECT RATIO IS NOT STRETCHED DOWN THE BLOCK AXIS. CSS Box Alignment §6.2's
#   `normal` fills the area only where the item has nothing else to say, and CSS Sizing §4.1's
#   definite-inline-implies-definite-block is something else to say. `grid_aspect_ratio_fill_child_height`
#   is the one-line demonstration: `width: 50px; aspect-ratio: 2` in a 100×100 grid is 50×25, and
#   stretching gave it the area's 100. The inline axis is clamped by the ratio-merged bounds FIRST
#   and the block axis derived from the clamped value, which is the same order LayoutTree.Absolute
#   uses and the reason `grid_aspect_ratio_fill_child_max_width` comes out 40×20 rather than 100×20.
#
# ⚠ And grid differs from flex here in a way worth keeping: a bound carried across the ratio DOES
# reach a grid item's stretched inline axis, and does NOT reach a flex item's stretched cross axis.
# `grid_aspect_ratio_fill_child_max_width` and `aspect_ratio_flex_column_stretch_fill_max_width` are
# both `max-height: 20px; aspect-ratio: 2` on a box whose parent fills its inline axis, and Chrome
# answers 40 wide for the grid item and 100 wide for the flex one. Flexbox §9.4 stretches an `auto`
# cross size unconditionally; Box Alignment's `normal` does not. `IsFlexItem` versus
# `IsFlexOrGridItem` in LayoutTree.Helpers is that difference and nothing else.
#
# ⚠ The last of the four was the §9 bucket's one survivor, and it was here rather than there because
# §9 was not what it was about. Its grid area is the whole padding box — the child names no line —
# so the containing block was already right and the box was still wrong: with `aspect-ratio: 3` and
# all four insets at 5% of a 400×300 box, Chrome reads the inline axis off the insets (360) and then
# lets the RATIO decide the height (120), ignoring `bottom` as over-constrained. This store solved
# both axes from their insets and answered 360×270, exactly as it did for the identically-named
# `absolute_aspect_ratio_*` families under flex and block. One rule in LayoutTree.Absolute for all
# three absolute paths, as predicted.
