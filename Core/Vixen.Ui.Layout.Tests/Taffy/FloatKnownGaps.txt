# Float fixtures in Taffy's corpus that Vixen does not yet get right.
#
# Same rules as the three gap files beside it: a name here is a fixture that LAYS OUT and disagrees
# with Chrome, given without the __{border,content}_box_{ltr,rtl} suffix, so one line covers up to
# four fixtures. TaffyFloatConformanceTests asserts both that every failure is listed here AND that
# the totals are the committed counts, so a line cannot quietly widen and a fix cannot quietly land.
#
# ⚠ **THIS FILE IS EMPTY AND THAT IS A WEAK RESULT, NOT A STRONG ONE — READ IT THE SAME WAY
# UnsupportedFixtures.txt SAYS TO READ THE OTHER CLEAN CONVERSIONS.** All 84 of these fixtures were
# ENGINE gaps: the store had no `float` field, so nothing here had ever been run, and the algorithm
# was written against these exact numbers over about a day. Of course they pass. A corpus that was
# already running and then went green would be evidence about the algorithm; a corpus that had never
# run and went green is evidence that somebody read the expectations, which is all it can be.
#
# The claim this corpus can honestly support is narrower and worth stating exactly:
#
#   · §9.5.1 placement, §9.5's non-overlap rule for formatting context roots, §9.5.2 clearance and
#     §10.6.3's contains-its-floats height are implemented and agree with Chrome on 84 fixtures,
#     including all 16 RTL variants and both box-sizing variants of each.
#   · The 8 `block_flow_root_*_float` fixtures in the block corpus agree too, which is the only part
#     of this that was cross-checked against a corpus written for something else.
#
# ⚠ **What it says nothing whatever about is INLINE interaction, which is the half of §9.5 everyone
# means by "floats".** `grep -c '<text' Corpus/float.xml` is 0. Not one fixture in this corpus puts
# text beside a float, so not one of them exercises the rule a float is famous for: shortening the
# line boxes that pass it. That sentence is still true of THIS corpus and always will be.
#
# ⚠ **The rule itself is no longer missing, and the fix had to bring its own oracle.** `LayoutTree.
# Inline`'s `WalkInlineLines` now asks the exclusion list for the band at each line's own top and
# height and shortens the line box to it, including §9.5's shift-downward clause when the band is too
# narrow for the first item. The expected numbers could not come from here or from
# `Tools/Vixen.TaffyTestGen` — Taffy has no inline layout, so there is nothing upstream to generate —
# so they were read out of Chrome 148 case by case. See `InlineFloatInteractionTests` and the FLOATS
# BESIDE LINES section of `InlineKnownGaps.txt`, which owns the residue.
#
#
# ── OWED, WITH NO FIXTURE IN ANY CORPUS TO PIN IT ────────────────────────────────────────────────
#
# ⚠ Kept here rather than in a commit message, because a reader who sees 84/84 and an empty gap list
# will otherwise conclude floats are finished. These are the places the implementation knowingly
# answers something other than what CSS 2.1 says, each because no fixture in 5 524 asks.

#                                 rather than against anything in this corpus; `InlineKnownGaps.txt`

#                                 rules 5 and 6) and the intrinsic width of a shrink-to-fit container

#                                 text leaf wraps around (#901) landed for a BLOCK-LEVEL leaf, which

# ── OWED ROWS THAT HAVE SINCE CLOSED, KEPT BECAUSE THE REFUTATION IS THE FINDING ─────────────────
#
# ⚠ All four are asserted in `FloatBlindSpotTests` now. TWO WERE ALREADY RIGHT, one was wrong for a
# different reason than this file gave, and the fourth turned out to be a SPECIAL CASE OF A DEFECT
# NOBODY HAD NAMED — which is the one worth reading.
#
# float-in-auto-centred-block     ⚠ **The diagnosis was half right and the stated consequence was
#                                 wrong.** The row said such a float "lands at the uncentred edge".
#                                 It did not: the float's own rectangle came out at the centred
#                                 block's content edge and looked perfect. What landed at the
#                                 uncentred edge was the EXCLUSION, because the float origin read an
#                                 `auto` margin as its stated zero while the position was written
#                                 from the resolved one — so the float was drawn at 150 and excluded
#                                 at 0..50, and only a box that has to avoid it can see the
#                                 difference. The reason given for not resolving it is refuted too:
#                                 the used width is `childWidth`, which is in hand, being the number
#                                 the StretchFit call is handed one line later.
#
#                                 ⚠ AND IT WAS A SPECIAL CASE. §9.5.1's rules 1 and 7 name the
#                                 float's CONTAINING BLOCK; the exclusion list is in the formatting
#                                 context ROOT's coordinates; `PlaceFloatChild` took the band's edge
#                                 as the float's edge without narrowing it to the container. So a
#                                 float in a block with a STATED left margin was placed at the root's
#                                 content edge and reported at x = −100 from its own parent, and a
#                                 right float in a 200-point box inside a 400-point root went against
#                                 the ROOT's right edge. Invisible to all 84 fixtures because
#                                 `float_bfc_avoids_float_from_sibling_subtree` is the only one that
#                                 nests a float at all, and the box it nests it in has no margin, no
#                                 padding and no width of its own.
#
# float-margin-collapse-through   CONFIRMED, and the row's own framing was the honest one: the
#                                 arithmetic was reasoned and is now measured. Both halves are
#                                 asserted at once because they fail differently — the float's border
#                                 box says the margin was spent, the cleared sibling below says the
#                                 exclusion's bottom edge included it.
#
# float-percentage-height         CONFIRMED. Asserted through a cleared sibling rather than off the
#                                 float, so a height that resolved in the geometry but not in the
#                                 exclusion list would still be caught.
#
# right-float-narrows-bfc-root    CONFIRMED: `AvoidFloats` really is symmetric. Both halves of the
#                                 pair are pinned now, because they are different branches — an
#                                 automatic width narrows beside the float and a stated one drops
#                                 below it, which is the distinction two of the ten left-floating
#                                 families exist to draw.
