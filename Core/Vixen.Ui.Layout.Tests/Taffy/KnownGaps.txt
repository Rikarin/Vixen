# Flexbox fixtures in Taffy's corpus that Vixen does not yet get right.
#
# Every name here is a fixture that LAYS OUT and disagrees with Chrome. That is a different thing
# from the fixtures TaffyStyleMap refuses, which ask for a property this store has no field for and
# are skipped with a reason; those are not listed. It is also a different thing from a translation
# bug — thirteen of the original failures were this bridge conflating `start` with `flex-start`, and
# those were fixed rather than listed. Anything written down here is believed to be Vixen's.
#
# Names are given without the __{border,content}_box_{ltr,rtl} suffix, so one line covers up to four
# fixtures — and not always all four. align_baseline_multiline_column, align_baseline_multiline_column2
# and padding_border_overrides_size_flex_basis_0_growable each fail in their two border-box variants
# and pass in their two content-box ones, because box-sizing decides whether the bug is reachable.
#
# TaffyFlexConformanceTests asserts both that every failure is listed here AND that the totals are
# exactly the committed counts — so a line cannot quietly widen to cover a new failure, and fixing
# any one of these turns the suite red until the count and the line are both updated.
#
# 206 at the corpus's first run; 158 now. Two rules closed the 48: CSS Sizing §5.2.2's distinction
# between a min-content size and a min-content contribution, and §5.1's min-over-max precedence.
# A closed bucket keeps its heading with the diagnosis that closed it, because the next person to
# read this file is more likely to be looking for how one of these was found than for a to-do list.

# ── CSS Flexbox §4.5, the automatic minimum size, when the content size comes from a DESCENDANT ──
#
# ⚠ MOSTLY CLOSED. This was the biggest bucket — seventeen families — and nine of them are gone,
# along with absolute_minmax_*, bevy_issue_10343_flex, and the two below that were only ever the
# same bug seen from a different side. 206 → 158.
#
# The rule was there; what was missing was the distinction CSS Sizing §5.2.2 draws between a box's
# min-content *size* and its min-content *contribution*. The contribution of a box whose preferred
# size is definite is that size — the contents are not consulted. Vixen asked every descendant for
# its min-content size, and an empty `width: 50px` box answered ZERO, because a box with no
# contents needs no room for them. So every floor computed from such a descendant was missing.
# See LayoutTree.MinContentContribution, and AutomaticMinimumSizeTests for the four hand-written
# cases — the corpus is not allowed to be the only witness to a rule this load-bearing.
#
# ⚠ Two things learned closing it, both of which broke fixtures before they were understood:
#   · A PERCENTAGE preferred size is not definite here. CSS Sizing §5.2.1 — a percentage against a
#     containing block whose size is not yet known behaves as `auto`, which is exactly this probe's
#     situation. Reading `width: 100%` as definite fails Yoga's Percent_within_flex_grow and
#     Taffy's percent_within_flex_grow, the same case in both corpora.
#   · A WRAPPING container's min-content main size is its widest item, not the sum (§9.9.1). This
#     was caught by YOGA alone — three AlignContent fixtures — and by nothing in Taffy's 2 208.
#     Both corpora earned their keep on this change.
#   · A box that CLIPS an axis contributes nothing along it but its own padding and border, because
#     its contents are scrollable overflow (§5.2.2) — the same sentence §4.5 already applies one
#     level out. Neither corpus moved by a single fixture with this rule present or absent. The
#     EDITOR SCREENSHOTS caught it: every box in the docking chain declares `overflow: hidden`, and
#     without the rule the shell laid out 2 385 points wide inside a 1 100-point window with the
#     inspector off the side. Three oracles, three different findings, no overlap.
#
# ⚠ What is left in this bucket is a DIFFERENT bug that was hiding behind the first one, and it is
# worth stating precisely because the floor is now right and these still fail. §9.2 step 9 says the
# HYPOTHETICAL main size is the flex base size clamped by the used min and max — and §4.5's
# automatic minimum *is* the used min. Vixen only ever consults it inside the two distribution
# passes, so an item that does not flex never sees its own floor. flex_basis_smaller_than_content_row
# is the clean case: `flex-basis: 50px` on a column wrapping a 100px box, no grow and nothing to
# shrink, so neither pass touches it and it stays 50 where Chrome says 100 — even though
# ComputeAutoMinMainSize now returns exactly 100 for it. The fix belongs with the §9.7 work below,
# because moving the floor up to the hypothetical size also changes what line breaking consumes.
flex_basis_smaller_than_content_column
flex_basis_smaller_than_content_row
