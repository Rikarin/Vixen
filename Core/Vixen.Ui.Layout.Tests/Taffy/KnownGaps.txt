# THE WHOLE LIFE OF THIS CORPUS. This header used to say "those are not listed" and leave it there,
# which is exactly the omission that let a skip read as a pass. It is also a different thing from a
# translation bug — thirteen of the original failures were this bridge conflating `start` with
# `flex-start`, and those were fixed rather than listed. Anything written down here is believed to
# be Vixen's.
#
# Names are given without the __{border,content}_box_{ltr,rtl} suffix, so one line covers up to four
# fixtures — and not always all four. Three lines here cover two apiece, and ⚠ THIS SENTENCE USED TO
# NAME THE WRONG AXIS FOR TWO OF THEM, which is worth a line because it is the kind of claim nobody
# re-measures. It read: "align_baseline_multiline_column, align_baseline_multiline_column2 and
# padding_border_overrides_size_flex_basis_0_growable each fail in their two border-box variants and

# the two align_baseline_multiline_column families fail in their two RTL variants and pass both LTR
# ones. DIRECTION decides whether that bug is reachable, not box-sizing — and saying so out loud is
# most of the diagnosis, because a wrapped column's line positions mirror correctly and only the
# items' alignment WITHIN a line does not. See their heading below.
#
# TaffyFlexConformanceTests asserts both that every failure is listed here AND that the totals are
# exactly the committed counts — so a line cannot quietly widen to cover a new failure, and fixing
# any one of these turns the suite red until the count and the line are both updated.
#

# LOOKED AT rather than by breaking. They were refused on `scrollbar-width` and had never run. A

#
# Six rules closed the first 144: CSS Sizing §5.2.2's distinction
# between a min-content size and a min-content contribution, §5.1's min-over-max precedence,

# ── CSS Flexbox §4.5, the automatic minimum size, when the content size comes from a DESCENDANT ──
#
# ⚠ MOSTLY CLOSED, IN THREE GOES. Seventeen families at the start, one left. The first nine went with
# the min-content contribution rule below, along with absolute_minmax_*, bevy_issue_10343_flex and
# two more that were the same bug from another side: 206 → 158. Two of the eight that remained went
# with §9.7's freeze rule, which is written up at the bottom of this heading: 94 → 86. ⚠ The last
# five went with three rules that are not this one at all — a minimum clamped after the measurement
# instead of before it, an absolute `flex-basis` a guard was throwing away, and §9.7's grow branch
# forgetting the automatic minimum the shrink branch beside it remembers. They are written up under
# "FOUR OF THE LAST FIVE" below, and the prediction this heading carried — "where the last six will
# be argued out too" — was wrong about every one of them.
#
# The rule was there; what was missing was the distinction CSS Sizing §5.2.2 draws between a box's
# min-content *size* and its min-content *contribution*. The contribution of a box whose preferred
# size is definite is that size — the contents are not consulted. Vixen asked every descendant for
# its min-content size, and an empty `width: 50px` box answered ZERO, because a box with no
# contents needs no room for them. So every floor computed from such a descendant was missing.
# See LayoutTree.MinContentContribution, and AutomaticMinimumSizeTests for the four hand-written
# cases — the corpus is not allowed to be the only witness to a rule this load-bearing.
#
# ⚠ Two things learned closing it, both of which broke fixtures before they were understood:
#   · A PERCENTAGE preferred size is not definite here. CSS Sizing §5.2.1 — a percentage against a
#     containing block whose size is not yet known behaves as `auto`, which is exactly this probe's
#     situation. Reading `width: 100%` as definite fails Yoga's Percent_within_flex_grow and
#     Taffy's percent_within_flex_grow, the same case in both corpora.
#   · A WRAPPING container's min-content main size is its widest item, not the sum (§9.9.1). This
#     was caught by YOGA alone — three AlignContent fixtures — and by nothing in Taffy's 2 208.
#     Both corpora earned their keep on this change.
#   · A box that CLIPS an axis contributes nothing along it but its own padding and border, because
#     its contents are scrollable overflow (§5.2.2) — the same sentence §4.5 already applies one
#     level out. Neither corpus moved by a single fixture with this rule present or absent. The
#     EDITOR SCREENSHOTS caught it: every box in the docking chain declares `overflow: hidden`, and
#     without the rule the shell laid out 2 385 points wide inside a 1 100-point window with the
#     inspector off the side. Three oracles, three different findings, no overlap.
#
# ⚠ THE SECOND HALF IS ALSO CLOSED, and the heading it used to carry was RIGHT about the mechanism
# and WRONG about where to apply it. §9.2 step 9 says the HYPOTHETICAL main size is the flex base
# size clamped by the used min and max, and §4.5's automatic minimum *is* the used min; Vixen only
# consulted it inside the two distribution passes, so an item that does not flex never saw its own
# floor. That much was correct. What the heading then predicted — that the fix was to move the floor
# into line breaking so the two "move together" — was measured and does not work on its own: it
# closes three families and breaks percentage_moderate_complexity and
# percentage_multiple_nested_with_padding_margin_and_percentage_values, exactly as the old note
# warned. The note's conclusion, "do not re-try the one-liner", was sound. Its diagnosis was not.
#
# ⚠ The floor reaches a non-flexing item through §9.7 STEP 2, not through line breaking. An item
# with no usable flex factor is FROZEN AT ITS HYPOTHETICAL MAIN SIZE, which is where §4.5's minimum
# has always been; nothing new has to be applied anywhere. flex_basis_smaller_than_content_row is
# `flex-basis: 50px` on a column wrapping a 100px box with nothing to grow into and nothing to
# shrink, and it freezes at 100. See DistributionStartSize and IsFrozenByInflexibility.
#
# ⚠ AND THE TWO PERCENTAGE FIXTURES WERE THE LARGER FIND, because they are not this rule's failure —
# they are ComputeMinContentSize being wrong and nothing having consumed it before. The probe
# answered 31.04 for a box whose true content height is 26.176, for two independent reasons:
#
#   1. It resolved a grandchild's `margin: 5%` against the box the probe was ENTERED from rather than
#      against the box the grandchild is actually inside — 5% of 194 where the containing block is
#      85.36. Fixed for the case where the intervening box has a definite width: see
#      ProbeContentWidth. A `width: 50%` box still contributes zero, which is CSS Sizing §5.2.1's
#      answer to the cycle rather than a stopgap.
#   2. A CHILDLESS box returns zero without its own padding and border, where the leaf-with-measure
#      branch and the clipping branch beside it both add theirs. Still true and still wrong; it
#      happens to under-report, so nothing observes it yet.
#
#   A third, in the same probe: it reads a GRID container as a flex row and sums all of its items
#   along one axis. gridflex_row_integration is four 20-wide boxes in a 2x2 grid — 40 in Chrome, 80
#   from the probe.
#
# ⚠ Because two of those three are still open, the §4.5 floor is CAPPED at the item's own flex basis
# whenever that basis was MEASURED rather than declared — LayoutResult.FlexBasisFromContent. The
# justification is an inequality, not a heuristic: a box's min-content size cannot exceed the size
# its own contents were just measured at, so a floor that comes out above such a basis is the probe
# being wrong. A DECLARED basis carries no such guarantee, which is why flex_basis_smaller_than_
# content_row is untouched by the cap. Remove the cap when the probe is fixed, and expect nothing to
# move; keep it until then, or an over-reported floor becomes a real box.
#
# ⚠ "EXPECT NOTHING TO MOVE" WAS MEASURED AND IS WRONG, and it is worth the two lines because the next
# person will otherwise repeat the experiment. Deleting the cap on the unclamped-flex-base branch
# costs FOUR grid fixtures (measured when grid stood at 1 896) and gains nothing anywhere: flex
# stayed at 2 190 / 66 and Yoga's 534 did not move. So the cap is load-bearing beyond the two probe
# defects above, and bevy_issue_9530 — which the §9.7 heading expected the cap to be holding back —
# was not waiting on it either.
#
# ⚠ percentage_flex_basis_cross_min_height CLOSED with §9.2's unclamped flex base, which is written up
# under §9.7 below. It sat here rather than there because its symptom is a cross-axis minimum, and it
# is the one fixture in this bucket that the base/hypothetical split reached.
#
# ⚠ <b>FOUR OF THE LAST FIVE HAVE NOW CLOSED, AND NOT ONE OF THEM WAS §4.5 REACHING A DESCENDANT.</b>
# This heading's last five entries turned out to be three unrelated rules and one survivor. That is
# the fifth time in this file that a bucket's real membership was somewhere else, and the tell this
# time was that every one of them names `flex_basis` or `min_size` in its own fixture name — a
# STATED bound, where this heading is about an AUTOMATIC one derived from content.
#
#   · ⚠ <b>`measure_child_with_min_size_greater_than_available_space` is a clamp applied after the
#     measurement it should have preceded.</b> A box's BLOCK size is a function of the INLINE size it
#     is actually given, and CSS Sizing §5.1 clamps that by the MINIMUM as well as the maximum.
#     `ConstrainMaxSizeForMode` has narrowed the offer by an item's own maximum since the beginning;
#     the minimum half was never written. Sixteen Ahem characters with `min-width: 200px` in a
#     100-point column were measured at 100, took two lines and made the item 20 tall; at the 200
#     they were always going to be given they take one and the item is 10, which is Chrome's answer.
#     The used inline size never moves — it was going to be clamped up to 200 on the way out either
#     way — so only the other axis changes, which is why this reads as a line-breaking bug and is an
#     ordering one. Grid found the same rule from the maximum's side, under
#     `grid_size_child_fixed_tracks`. See LayoutTree.Helpers.ConstrainMinSizeForMode.
#
#   · ⚠ <b>`flex_basis_unconstraint_column`, `taffy_issue_696_min_height` and
#     `absolute_child_with_max_height_larger_shrinkable_grandchild` are one guard, and the
#     REGRESSION it caused is the rule.</b> §9.2 step 3 makes a flex base size out of the declaration
#     whenever the declaration is definite; this store additionally required the CONTAINER's main
#     size to be definite, which is Yoga's guard ported with the rest of the order of operations. An
#     absolute `flex-basis: 50px` on the only child of a container with no main size fell through to
#     the content branch, the child was empty, and a declaration of 50 became a measurement of 0.
#     ⚠ Relaxing that on both axes measures +12 and −6: it also opens `flex_basis_unconstraint_row`
#     and both content-box halves of `padding_border_overrides_size_flex_basis_0_growable`. Those two
#     fixtures are the same declaration as `_column` on the other axis, and Chrome answers 50 for the
#     column and 0 for the row — because a row container's main axis is the one §9.9.3's CONTRIBUTION
#     rules govern, and there an item's contribution is its own outer max-content size (zero, for an
#     empty box) clamped from ABOVE by its flex base when the item cannot grow. `flex-basis` is a
#     ceiling there, not a size. A column container with an indefinite height has no such rule to
#     apply: it runs §9.3–§9.7 with indefinite free space and every item freezes at its hypothetical
#     main size. Scoped to the block axis the same change is +12 and −0. The percentage half of the
#     guard stays on both axes, and it is the half that was always load-bearing (§5.2.1).
#
#   · ⚠ <b>`flex_basis_smaller_then_content_with_flex_grow_large_size` was §9.7's own asymmetry.</b>
#     Step 4b clamps a flexed item by its USED minimum, and for a flex item `min-width: auto` IS
#     §4.5's automatic one — when growing as well as when shrinking. The two halves of
#     `DistributeFreeSpaceFirstPass` had drifted apart: the shrink half asked
#     `BoundAxisWithAutoMin`, the grow half asked `BoundAxis` and saw stated bounds only. So a
#     growing item floored by its content never registered as a MIN VIOLATION, was never frozen by
#     step 4c, and the space its floor took was never returned to the pool — the second pass applied
#     the floor to the item anyway and the line overflowed by the difference. Two `flex-grow: 1;
#     flex-basis: 0` items in a 100-point row around a 70-point box and a 20-point one: the pool
#     splits 50/50, the first violates its 70 floor, and Chrome freezes it there and gives the whole
#     remaining 30 to its sibling. This is the same mistake InitialFreeSpace was written to fix, one
#     branch away from where it was fixed.
#
# ⚠ The survivor is the one this heading was always least likely to be right about, because it is the
# only one whose two failing variants really are the border-box pair. `padding_border_overrides_size_
# flex_basis_0_growable` is two `flex-grow: 1; flex-basis: 0px` items in a shrink-to-fit row, the
# first with 22 points of horizontal padding and border around a `width: 12px`. Chrome makes the
# container 34 and the items 28 and 6; this store makes it 22, 22 and 0. The content-box pair passes
# with 46, 34 and 12, and the arithmetic that produces both is §9.9.1's: the container's max-content
# main size is the sum of the items' max-content CONTRIBUTIONS — 22 + 12 border-box, 34 + 12
# content-box — after which the free space over the items' flex BASES (22 and 0) splits evenly. The
# store agrees about the bases and disagrees about the second item's contribution, counting its
# `flex-basis: 0` where Chrome counts its `width: 12px`. It is a contribution rule, not a floor, and
# it belongs under a heading this file does not yet have.
padding_border_overrides_size_flex_basis_0_growable

# ── CSS Flexbox §9.7, resolving flexible lengths: the free space is not the line's size ──
#
# ⚠ THE HEADING THIS BUCKET CARRIED WAS WRONG, and refuting it is what closed most of the file. It
# said "the loop that re-runs distribution after clamping is what is missing, not the clamp." That
# loop was never missing — DistributeFreeSpaceFirstPass is exactly it, and it is correct. What it
# was handed was a pool that had already paid for the clamp.
#
# §9.3 breaks lines by each item's outer HYPOTHETICAL main size: the flex base clamped by its used
# min and max. §9.7 step 3 builds the free space out of a DIFFERENT sum — the frozen items' target
# sizes and the unfrozen items' unclamped FLEX BASE sizes. Vixen had one field, FlexLine.SizeConsumed,
# serving both, so every clamp was charged twice: once by shrinking the pool it came out of, and
# again by the pass that re-applied it to the item. There are now three sums, and the comments on
# FlexLine say which question each answers. InitialFreeSpace also implements step 2 properly, which
# removes a frozen item's flex FACTOR as well as its size — leaving the factor in was a latent
# divide-by-zero that Yoga's Child_min_max_width_flexing hit as a NaN the moment step 2 arrived.
#
# ⚠ THE SECOND HALF IS ALSO CLOSED, and the refusal that filed it was right about the diagnosis and
# wrong about how far it reached. `results[child].ComputedFlexBasis` WAS NOT A FLEX BASE SIZE: it was
# read back out of a trial layout that had already clamped it, so an empty `min-width: 60px` div
# reported 60 where §9.2 says its base is 0. With base == hypothetical the item was never frozen and
# no amount of redistribution could recover the difference — `min_width`'s two flex-grow:1 children in
# a 100px row came out 80 and 20 where Chrome says 60 and 40.
#
# The fix is the one that was scoped: LayoutResult.UnclampedMeasuredDimensions records each axis's
# measurement BEFORE BoundAxis, written at every site that writes MeasuredDimensions — Steps, Layout's
# STEP 9, Block, Grid, Inline, InlineItems and the measurement cache, which has to replay it for the
# reason it already replays the collapsible margins. LayoutTree.SetMeasuredDimension exists so the two
# cannot be written apart. 2 178 → 2 190; three families here, and
# percentage_flex_basis_cross_min_height out of the §4.5 bucket above.
#
# ⚠ THE HALF THE SCOPING MISSED IS THAT `mainAxisOverflows` WAS READING THE SAME FIELD, and it is the
# reason a first attempt banked +12 with four regressions. STEP 3 added up the items' flex BASES to
# decide whether the main axis overflows. That is §9.3's question, and §9.3 asks it of the outer
# HYPOTHETICAL sizes; the two agreed only because the base was the clamped measurement. Once the base
# became real, `gap_column_gap_wrap_align_stretch` saw five zero-basis items as 20 points of gap in a
# 300-point row, concluded nothing overflowed, and stretched every item to the container's full height
# instead of halving it between the two lines it still broke into — four Taffy fixtures and Yoga's
# Column_gap_wrap_align_stretch. The sum is now taken in the walk that computes each item's automatic
# minimum, out of HypotheticalMainSize, and ComputeFlexBasisForChildren no longer returns a total.
#
# ⚠ THE TWO THAT DID NOT CLOSE ARE NOT THIS RULE, and the prediction that they would is refuted:
#   · taffy_issue_696_min_height could not have moved. Its item declares `flex-basis: 0px`, so its
#     basis comes off the declaration and never touched a measurement. `min-height: 100px` around a
#     200pt non-shrinking child: Chrome keeps the item at 100 and lets the child overflow, Vixen
#     answers 240. The item's hypothetical size is already 100; what grows is the CONTAINER, which
#     sizes itself off the child's measurement rather than the item's target size.
#     ⚠ CLOSED, and this note had the shape right and the cause exactly inverted. Its basis "comes
#     off the declaration" was the assumption; the declaration was being IGNORED, because the guard
#     on §9.2 step 3 also demanded a definite container main size and this container has none. So
#     the item fell through to the content branch, measured 240, and the container took it. Written
#     up in full under the §4.5 heading above, with the two fixtures that decide which axis it
#     applies to.
#   · bevy_issue_9530 is content-measured, so the new base does reach it, and it still shrank both
#     items proportionally where Chrome freezes the text box and overflows. It was not the §4.5 floor
#     cap either. It was the floor's own measurement, in the block axis, and it is CLOSED — see the
#     downstream-regression heading below.

# ── aspect-ratio against min/max and stretch ──
#
# ⚠ CLOSED. Sixteen families, the largest bucket left, and the diagnosis this heading carried was
# right as far as it went: "the ratio is applied, but not re-applied after the cross size is clamped
# or stretched, so the transfer goes one way only." What it did not say is that "the transfer" is
# THREE rules, and that the same sixteen names in the grid and block corpora were the same three.
# 158 → 94 here, 340 → 324 in GridKnownGaps.txt, and 20 → 0 in BlockKnownGaps.txt.
#
#   1. A MINIMUM OR MAXIMUM CROSSES THE RATIO (CSS Sizing §4.1, §5.1). `max-height: 20px` with
#      `aspect-ratio: 2` IS a `max-width` of 40. LayoutTree.Helpers.ResolveAspectBounds merges each
#      bound with the other axis's transferred one — larger wins for a minimum, smaller for a
#      maximum — which leaves the pair self-consistent, so clamping the axis that was decided first
#      and deriving the other from it needs no second clamp. Transferring one way only is exactly
#      the asymmetry the heading described. This is where aspect_ratio_flex_row_fill_max_width's
#      40x20 comes from; it used to be 80 wide.
#
#   2. THE BOUND TRANSFERS ONLY INTO AN AXIS THE RATIO DECIDES. An axis the flex algorithm stretched
#      to the line was decided by §9.4, not by the ratio, and a bound carried across has no standing
#      on it — aspect_ratio_flex_row_stretch_fill_max_height is 40x100 and not 40x20. Its own
#      maximum still applies. `axisSizeIsImposed` on BoundAxisWithinMinAndMax is this rule.
#
#   3. WHICH AUTOMATIC MINIMUM ARGUES WITH THE TRANSFERRED MAXIMUM IS THE PARENT'S DECISION, and it
#      is the one that stops rule 1 being applied everywhere. aspect_ratio_flex_column_fill_max_height
#      and block_aspect_ratio_fill_max_height are the same box — `max-width: 40px; aspect-ratio: 2`
#      around the same eleven syllables of Ahem — and Chrome answers 40x20 under a flex parent and
#      40x60 under a block one. A block box gets §4.1's content-based automatic minimum, which its
#      text floors at six lines; a flex item gets Flexbox §4.5's, which its own maximum caps. Two
#      formatting contexts, two answers, from one declaration.
#
# ⚠ The five absolute_aspect_ratio_* families that used to sit at the bottom of this bucket were the
# same rules reached through LayoutTree.Absolute, which flex, block and grid all share — which is
# why closing them here closed BlockKnownGaps.txt entirely and took grid's copy with it. The
# `overrides_height_of_full_inset` family needed one thing more, and it is written up where it was
# last diagnosed: a full set of insets plus a ratio is over-constrained, and CSS Position §10.6.4
# drops the end inset rather than the ratio. All three corpora answered 360x270 for it; Chrome says
# 360x120.

# ── Baseline alignment past the simple case ── the wrap-reverse half is CLOSED ──
#
# ⚠ <b>The one line this heading carried — "a wrapped column's per-line baselines, and baseline under
# wrap-reverse" — named two things and they have nothing to do with each other.</b> The wrap-reverse
# half was one axis question and closed in two places; the column half is not about lines, or about
# per-line anything, and is written out below with what is actually known about it.
#
# ⚠ <b>UNDER `wrap-reverse` THE OFFSET IS THE DESCENT, NOT THE ASCENT.</b> §8.3 places the item with
# the largest distance between its baseline and its CROSS-START margin edge flush against the line's
# cross-start, and `wrap-reverse` moves that edge to the bottom — so the distance that decides the
# alignment is the descent. This store lays wrap-reverse out forwards and mirrors it afterwards
# (STEP 9: `newTop = container − oldTop − height`), and no mirror can produce that: reflecting boxes
# whose TOPS are offset by the ascent difference gives boxes whose BOTTOMS are offset by the ascent
# difference, and a set of boxes with spread-out bottoms is a set whose synthesised baselines are not
# aligned. `align_baseline_wrap_reverse` is four childless boxes, so every baseline is a bottom edge
# and every descent is zero: Chrome puts all four bottoms on their line's bottom, the mirror put the
# short ones 20 points above it. ⚠ The reflection is right for the tallest item in each line and
# wrong for every other one, which is exactly why this looked like an align-content rounding error.
# See LayoutTree.Align.
#
# ⚠ <b>AND AN OUT-OF-FLOW CHILD IS NOT IN A LINE, SO ITS `baseline` IS NEVER FLIPPED AT ALL.</b>
# `absolute_layout_align_self_baseline_wrap_reverse` is a single absolutely-positioned box with
# `align-self: baseline` and no insets, and Chrome puts it at y=0 where this store put it at y=80.
# It participates in no baseline group, so CSS Align §9.3 aligns it by its FALLBACK alignment, and
# the fallback for `first baseline` is `start` — the writing-mode-relative keyword. Only the
# FLOW-relative pair, `flex-start`/`flex-end`, is reversed by the wrap direction.
# LayoutTree.Absolute folded `baseline` into the same arm as `flex-start` and `stretch`, which are
# flow-relative and do belong there. One keyword excluded; four fixtures.
#
# ⚠ <b>WHAT IS LEFT IS NOT A BASELINE BUG AND IS NOT ABOUT LINES.</b> The two
# `align_baseline_multiline_column` families fail in their RTL variants only — see the preamble,
# which used to say border-box and was wrong. `IsBaselineLayout` returns false for a COLUMN
# container, correctly: the cross axis is then the inline axis, baselines are not parallel to it, and
# §9.3's fallback applies. Both fixtures' LINE positions mirror correctly (line one on the right,
# line two on the left) and both containers' sizes are right; the only disagreement is where an item
# sits WITHIN its line. This store puts it at the RTL flex-start — the line's right edge, 70 and 10 —
# and Chrome puts it at the line's left edge, 50 and 0, while mirroring the same items' own children
# correctly one level down. Neither `start` nor `flex-start` is left in RTL, so the fallback story
# does not explain Chrome and something else is deciding it. Four fixtures, no rule, and it should
# not be guessed at: baseline alignment in a column container is under-specified and Chrome and
# Firefox are known to disagree about it, so a fixture-level guess here is likely to be a fifth entry
# in this file's list of headings that were believed because they were plausible.
align_baseline_multiline_column
align_baseline_multiline_column2

# ── A percentage gap on an auto-sized container, which is cyclic ── CLOSED ──
#
# The heading was right — "column-gap:20% on a shrink-to-fit row: the gap depends on the width that
# depends on the gap" — and it stopped one sentence short of the fix.
#
# ⚠ <b>CSS Sizing §5.2.1 breaks the cycle by resolving the gutter as ZERO while the size is being
# decided, and this store was already doing that by accident.</b> CalculateFlexLine is handed NaN
# under a content-based main size, so a percentage gutter comes out zero and `line.SizeConsumed` —
# the number the box's own size is taken from — is a gapless one. That part was right. What was
# wrong is everything after it: the gutter became resolvable the moment the box's size existed,
# JustifyMainAxis re-resolved it, laid the items out with it, and `line.MainDim` GREW to hold a
# gutter the box had already been sized without. The gutter was self-fulfilling and nothing ever
# shrank.
#
# ⚠ <b>The gutter is charged to the LINE, which is what §9.7 distributes over, and not to the BOX,
# whose size was already decided.</b> Three 20-point items with `column-gap: 20%`: the box is 60,
# the gutter is 20% of 60 = 12, the line needs 84 in a 60-point box, and the items shrink to 12
# apiece. The three fixtures are the three ways that ends — everything shrinks (12/12/12), nothing
# does (`_unshrinkable`, 20/20/20 with the last item ending at 84 while the box stays 60), and one

# ⚠ Not applied to the CROSS-axis gutter, which is the same cycle on the other axis. No fixture in

# ── align-content: stretch across the lines of a wrapped row ── CLOSED ──
#
# ⚠ <b>An item in a MULTI-LINE container is stretched to its LINE, and `flex-wrap: wrap` makes a
# container multi-line whether or not anything wrapped.</b> §9.4 step 7 hands a stretched item the
# container's inner cross size and opens "if the flex container is single-line"; step 8 sizes a
# multi-line container's lines from the largest HYPOTHETICAL cross size on each, which is the
# unstretched one. Pre-stretching answers the question the line is about to ask with the number the
# line was supposed to produce.
#
# The guard here read `!(isNodeFlexWrap && mainAxisOverflows)` — Yoga's, which only declines to
# stretch when the line has already overflowed. `align_content_stretch_row_wrap` is one line holding
# a 150-point-tall grandchild in a 100-point container and it does not overflow the MAIN axis at
# all: the item was measured at the container's 100, the line took 100 from it, and `align-content:
# stretch` then had nothing left to stretch. Chrome's line is 150 and the item overflows the box.
# The item is stretched to its line in LayoutTree.Align, which is where it always belonged.

# ── Taffy's own regression fixtures, from downstream bug reports. NOW DIAGNOSED. ──
#
# ⚠ THE PREDICTION THIS HEADING MADE WAS RIGHT TWICE OVER: "the ones most likely to collapse into
# the buckets above once one of those is fixed." bevy_issue_10343_flex went with the §4.5 descendant
# rule. bevy_issue_9530 was read as §9.7 and as waiting on the unclamped flex base, and was neither —
# see its own note below, which closed it.
# Two of the remaining three are diagnosed below and one of them was a bug of its own, which is the
# argument for reading downstream regression fixtures rather than filing them: they are the ones
# nobody wrote a spec-shaped test for.
#
# ⚠ bevy_issue_8082 IS CLOSED and was nothing to do with any bucket here. `align-items: flex-start`
# placed an item at its line's cross edge WITHOUT its own leading cross margin. The line's height is
# measured with the margins in it, Align.Stretch beside it adds the margin and Align.FlexEnd
# subtracts the trailing one — flex-start alone added only the relative inset. Four 50px boxes with
# `margin: 10px` came out exactly 10 too high, each. One line in LayoutTree.Align, and
# FlexibleLengthResolutionTests has it written out where no fixture is needed to see it.
#
# ⚠ bevy_issue_9530 IS CLOSED, and the line this heading left for whoever came next is what closed
# it. It read: "the floor this box needs is not being capped away — it is not being computed, or not
# being consulted, on the shrink path." It was not being computed, and the reason is one axis of one
# probe. `ComputeMinContentSizeUncached` measured a leaf's BLOCK-axis min-content size with the width
# undefined, so a text reported the height of a single line — there is no min-content height of a
# paragraph on its own, only the height it takes at the inline size it has. §4.5's floor for the
# grow box was therefore one line where Chrome's is 420, the box did not freeze, and both children
# shrank proportionally. Measured at the containing block's inline size instead, it freezes, the
# whole overflow goes to the 20pt box and the container overflows as Chrome draws it.
#
# ⚠ It cost a second change to land, and the second one is the interesting half. Measuring at the
# real width makes every block-axis §4.5 floor bigger, and a bigger floor overrules a smaller
# aspect ratio: `aspect_ratio_flex_column_stretch_fill_max_height` went red on the measurement alone.
# §4.5's CONTENT SIZE SUGGESTION is clamped through the ratio by the cross MIN AND MAX — a different
# clamp from the transferred size suggestion, which needs a definite cross size where this needs only
# a bound. Both halves together are +4 here and +4 in grid; the first half alone is +4 and −4.
#
# ⚠ bevy_issue_7976_{3,4}_level ARE A PERCENTAGE CYCLE IN THE FLEX-BASIS TRIAL LAYOUT, and they are
# the one thing here that is not §9.7. A `min-width: 40px` item wrapping a `width: 100%` child should
# be 40 wide: during the item's own intrinsic measurement its width is not yet known, so CSS Sizing
# §5.2.1 makes the child's percentage behave as `auto` and the content comes to nothing. Vixen lays
# the item out at the space it was OFFERED — 190 — so the child takes 100% of 190 and the item
# reports 190 as its content width. MinContentContribution already implements exactly this rule for
# the probe and says so in its own comment; ComputeFlexBasisForChild's trial layout does not. The
# fix is to stop a FitContent/MaxContent measurement handing a definite size down for percentages to
# resolve against, which is a change to how availability propagates and wants its own pass.
# bevy_issue_7976_reduced passes, and the only difference is that it has no percentage child.

# ── THE FLEX BASE SIZE OF A MEASURED ITEM IS TAKEN UNDER THE CONTAINER'S AVAILABLE SIZE, NOT AT
#    MAX-CONTENT ── one family, and it only shows when §4.5 is opted out ──
#
# ⚠ <b>NEWLY VISIBLE, NOT NEWLY BROKEN.</b> `measure_child_with_flex_shrink_hidden` had never run:
# it writes `scrollbar-width="15"` beside `overflow: hidden`, and TaffyStyleMap refused the whole
# fixture on a declaration that reserves no gutter and could not have moved a box. See
# UnsupportedFixtures.txt for the other 120 that were in the same position.
#
# A 100pt row holding a 50pt box and a text of five ten-character words. Chrome: 9 and 91. Vixen:
# 33 and 67. The arithmetic says exactly where the disagreement is. §9.2 step 3E makes the flex base
# size of a content-sized item its MAX-CONTENT size, which here is 500; shrinking 450 across
# weighted bases of 50 and 500 gives 9.09 and 90.9, which is Chrome's answer to the point.
# ComputeFlexBasisForChild instead hands the child the container's own available width as a
# FitContent offer — the `if (!isMainAxisRow || mainOverflow != Overflow.Scroll)` clause in
# LayoutTree.Steps, whose comment says in as many words "the specification says nothing about
# `overflow` here; every major browser does this" — so the text measures at 100, and shrinking 50
# across bases of 50 and 100 gives 33.3 and 66.7. Which is what came out.
#
# ⚠ THE REASON NO OTHER FIXTURE CATCHES IT IS THE PART WORTH KEEPING. Both readings give the same
# answer whenever §4.5's automatic minimum applies, because the item is floored at its min-content
# size either way — `measure_child_with_flex_shrink`, the same fixture without the `overflow`, is
# green under both. An item only sees the difference by OPTING OUT of the automatic minimum, and the
# way to opt out is `overflow` other than `visible`, which is the exact attribute pairing that had
# never been translated. One property's refusal was hiding the only witness to another property's
# arithmetic.
#
# Not a one-line fix, and the existing comment is why: that clause is deliberate and is load-bearing
# for Yoga's 534, which are the fixtures Vixen's flex algorithm was originally judged against.
# Chrome's own behaviour is the spec's. The honest shape is to keep the offer for the measurement
# but record the unclamped max-content size separately as the base — the same separation
# LayoutResult.UnclampedMeasuredDimensions already made once, one question further out.
