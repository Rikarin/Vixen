# Generator and analyzer projects that no packable library carries into its package, deliberately.
# One project name per line; everything after the first space is why.
#
# ⚠ This list can only SHRINK. `CheckArchitecture` fails on a name that is here and has become
# packed, exactly as `docs/ComponentGeneratorExempt.txt`, `docs/WhitespaceExempt.txt` and
# `docs/DocCommentExempt.txt` do — so a line that has done its job cannot sit here hiding the next
# library to stop shipping its generator.
#
# ⚠ What being on this list means: a consumer with a `PackageReference` to the sibling library gets
# the attributes the generator reads and none of the code it writes, and NOTHING IN THIS TREE CAN
# NOTICE — an analyzer does not flow through a `ProjectReference`, so every in-tree consumer names
# the generator itself and the only place the answer exists is the `.nupkg` bytes. For the two
# below that is the right outcome; for `Vixen.Ecs.Generators` and `Vixen.Editor.Inspector.Generator`
# it was not, which is #1165. ⚠ `Vixen.Core.Syntax.Generator` was a third entry here and is gone:
# it was a BLOCKER rather than a decision — `VXS0001` fired on every compilation with no
# `Syntax.xml`, so packing it would have warned every consumer that is not writing a language —
# and #1188 closed it by making the diagnostic read `VixenSyntaxXmlRequired`. `Vixen.Core.Syntax`
# now packs it, which is what its own description always promised.
#
# ⚠ The question to ask before packing one: what does it emit into a compilation that declares none
# of its attributes? A generator that answers "nothing" is safe to ship. One that answers "the same
# code every time" ships a duplicate, and one that answers "a warning" ships a warning.

Vixen.Ecs.Generators QueryArityGenerator emits at post-initialisation and its output depends on nothing in the compilation, so a consumer that also ran it would get a SECOND copy of the same partials and the same WorldQueryExtensions in namespace Vixen.Ecs — a duplicate type rather than a missing one. The generators meant for a user's own compilation live with the layers that need them: [Component] registration is Vixen.Engine.Generators, which Vixen.Engine packs. ⚠ #1165 named this one "the one that matters most" on the belief that it writes the code behind [Component]; it does not, and that claim is refuted.

Vixen.Core.IO.Analyzers VXIO0001 is a rule about THIS repository's own code — only virtual paths in engine code, doc 10 § Cross-platform discipline — and Directory.Build.props:485 applies it to Core/** alone. Platform/, Editor/, Tools/ and Raven/ deliberately do not get it, because translating a virtual path to a host path is what those layers are for. Shipping it would hand a game's own code a warning for calling System.IO.Path, which is the opposite of the rule's intent, and with TreatWarningsAsErrors an error.


Vixen.Core.Diagnostics.Analyzers VXLG0001 is a rule about THIS repository's own code — doc 13 § Discipline's "every catch either handles or logs with the exception object" — and Directory.Build.props applies it to Core/** alone. It reports on ordinary code rather than on a marked member, so shipping it would hand a game's own code a warning for a catch this rule was never written about, and with TreatWarningsAsErrors an error. ⚠ That is exactly why it is a project of its own and not a second rule inside Vixen.Core.Analyzers, which Vixen.Core DOES pack: VXHP0001 can ship because it is silent in a compilation that marks nothing [HotPath], and this one cannot.
