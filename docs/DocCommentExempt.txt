# Files holding a doc comment block that describes a member other than the one it is attached to,
# and that nobody is fixing today.
#
# ⚠ This list exists so that the rule can run at all. Two comments landed stapled above the wrong
# member in one batch (#866) — an agent inserting a new member between an existing comment and the
# member it documented — and a green build, a green 1 333-test suite, a clean
# `dotnet format whitespace` and a clean `dotnet format style --severity warn` all passed over both.
# A duplicated `<summary>` is not a Roslyn diagnostic at any severity, and the one diagnostic that
# names the other half needs `GenerateDocumentationFile`, which `Directory.Build.props` turns off for
# the whole tooling profile. So the reader was the only instrument, and a stapled comment is exactly
# what misleads a reader.
#
# Sixty-four blocks in fifty-one files were already wrong the day the rule was written. ⚠ They are not
# all cosmetic: `Editor/Vixen.Editor.Ui/Commands/KeyChord.cs` carries `MacGlyphs`' entire block above
# `MacWords`, so one public formatter is undocumented and the other is described twice — the #866
# defect, live, in shipped code, found by the rule's first run. #879 is the task to empty this list.
#
# `nuke CheckDocComments` fails when
#
#   * a file not listed here has a stapled block — that is the gate,
#   * a file listed here no longer has one: delete the line in the same commit.
#
# So this file should only ever shrink, and a commit that grows it is a commit that stapled a comment.
# `./build.sh CheckDocComments --update-exemptions` rewrites it, and is deliberately a command
# somebody runs: a gate that wrote its own exemptions would fail on nothing, forever.
