# Vixen — Implementation Overview

A single-page reconciliation of **what the plan asks for**, **what exists in the repository**, and
**what is holding the rest up**.

Sources: every file under [`docs/plan/`](plan/), [`docs/manual/`](manual/),
[`docs/rhi-backend-mapping.md`](rhi-backend-mapping.md), the per-project `README.md` files, the
`Directory.Packages.props` register, the Nuke targets in `build/`, and `.github/workflows/`.

> **Where the sources disagree, the code wins.** Every row below is marked against the code, and a
> divergence from a document is called out in the note. This file is the *only* place that carries
> per-feature status: [`14-roadmap.md`](plan/14-roadmap.md) keeps the phase boundaries and their exit
> criteria and points here, and the reasoning behind any one subsystem lives in that subsystem's
> `README.md`. Three places recording the same thing is how they come to disagree.

## Legend

| | Meaning |
|---|---|
| ✅ | Built, tested, and gated |
| 🟡 | Partially built — the named half works, the rest is listed under *Owed* |
| ⬜ | Not started — no project, or a project with no implementation |
| ⛔ | Blocked — cannot start until something else exists or a decision is made |
| ✂️ | Deliberately cut or postponed past 1.0 |

| World serialisation | ✅ | Core/Vixen.Engine | `WorldSerializer` + `WorldContent`, in `Vixen.Engine` because the pieces are: the ECS references no serializer by design and the binders are `SceneComponentRegistry`'s. K1's first downstream item, and the dependency was real — until the scene format existed this could only have written raw chunk memory, which is `WorldSnapshot` and is not a format. ⚠ **Entity handles are not stored**, so `Parent`/`Child`/`Sibling` are never written and the hierarchy travels as a table of indices rebuilt by the link pass; a game component holding an `Entity` is the caller's to translate, and `Capture`/`Restore` hand it the table to do it with. A component with no `[DataContract]` is named in `Dropped` rather than refused or lost in silence. The oracle is capture ∘ restore = identity on the bytes, which needs the restore to number entities in the content's order — a digest cannot be one, because `WorldDigest` hashes ids and a restore reassigns them |

| **Virtual cameras** (shots, body/aim stages, director, blending, noise, impulse) | ✅ | Core/Vixen.Engine | [plan/26](plan/26-virtual-cameras.md). A Cinemachine-shaped system: `VirtualCamera` shots picked on priority by a `CameraDirector` beside the real `Camera`, blended with five curves and a per-pair table. Four bodies (follow with four binding frames, screen-space framing, orbit, hard lock) and four aims (composer with dead and soft zones, hard look, POV, match target), each a chunk sweep over the shots that carry it — which stage a shot uses is an archetype question, not a branch. Damping is exponential and *exactly* frame-rate independent, rotation included, and a damping time means one thing everywhere: 99 % of the error removed. Framing corrections are the difference of two arctangents rather than the arctangent of a difference, which is the part that is wrong at the edges of the frame if you do not. Value-noise handheld shake whose amplitude is a hard bound, impulses that are an initial velocity with distance falloff and a propagation delay, a box confiner, and obstacle avoidance through an `ICameraOcclusion` seam because the engine references no physics. Runs in `LateUpdate` reading targets through `Hierarchy.ResolveWorldMatrix`, so a camera never lags its subject by a frame, and writes the camera's *local* transform so `PreRender` resolves the rig with it. 50 tests, and a hundred shots with every stage between them allocate nothing across five hundred frames |

## 1.11 Editor

> **Phase 6's exit sentence is met.** The editor opens a project, imports assets, builds content,
> edits a scene, saves, and runs the game — entirely in `Vixen.Ui`, with no other toolkit anywhere in
> the dependency graph. Everything Phase 6 listed beyond that sentence has since landed too — the
> asset editors, the profiler, the debugger, the plugin host and the animation graph are all projects
> now. What is left of that phase is **`PublishEditor`** with signing and notarisation, **golden
> screenshots** for editor layouts, and the **editor-shell performance bar**, which is unmeasured.
>
> ✅ **The viewport draws meshes.** This box used to say it drew lines only, and it was stale within a
> day of being written: `SceneShape` names either a built-in primitive or a mesh reference, so a
> hundred instances of one rock are one instanced draw exactly as a hundred cubes already were, and
> `ProjectMeshSource` turns a reference into vertices out of the project's own artefact store rather
> than out of a content build — waiting for a build to look at a level would make the viewport a
> function of the build rather than of the files. ⚠ An unloaded mesh draws **nothing** rather than
> falling back to its shape, and `SceneMeshes.Waiting` says how many: an entity that changed
> appearance while its mesh loaded is a scene that looks different depending on how fast the disk is.
>
> ✅ **And shades them with their material.** The line above used to end "what is still owed is a
> *material*". `ProjectSurfaceSource` reads the chunk `MaterialImporter` wrote and `MaterialSurface`
> reduces its feature tree to what a preview can shade with — a base colour, a metalness, a roughness
> and what it emits — which reach the instance as two more vertex attributes, so entities of different
> materials sharing a shape are still one draw. `MeshInstanced.rvn` shades them with GGX, a
> height-correlated Smith visibility and Schlick. ⚠ **What the reduction drops is textures**: a base
> colour map multiplies a tint and this pipeline has no descriptor set to sample one through, so a
> material whose map is a brick comes out its tint. Clear coat, sheen and the rest are passed over
> silently, because a material with a clear coat is still one whose base colour the viewport should
> draw. ⚠ **An entity naming no material is drawn exactly as it was**, because the neutral surface is
> a fully rough dielectric — which is the one directional term this box used to describe, to within a
> rounding. The payoff nobody planned: the **Roughness** view mode was declared-and-disabled because
> "roughness needs a material to read one off, and there are none", and it enabled itself.

# Part 3 — Dependency tree for the unimplemented work

a wave is a set of tracks that can run in parallel. An arrow `A → B` means B cannot start (or cannot
be finished honestly) until A lands.
