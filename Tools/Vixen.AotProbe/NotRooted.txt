# Runtime assemblies Tools/Vixen.AotProbe does NOT root, and that `CheckAot` therefore asks nothing
# about. One assembly name per line; everything after the first space is why not yet.
#
# ⚠ This list can only SHRINK. `CheckAot` fails on a name that is here and has become rooted, and
# on a net10.0 non-test assembly under Core/ or Platform/ that is neither rooted nor here — so a new
# runtime assembly cannot join the uncovered set in silence. The rule is build/AotRootingRule.cs and
# #506 is the expansion.
#
# ⚠ Being on this list is NOT "excluded from AOT". Many of these are in the probe's publish graph
# transitively, so ILC compiles whatever `Main` reaches inside them; what they do not get is the
# ROOTED question — is this assembly publishable ahead of time, rather than is one path through it
# clean — which is the only question the probe exists to ask (Tools/Vixen.AotProbe/README.md
# § Why it roots rather than calls).
#
# ⚠ Measured 2026-09-10: 84 of 95 rooted, 11 here. It was 29 and 66, and every one of the fifty-three
# that moved was clean on the first ILC publish — including Vixen.Core.Yaml, which this list
# predicted "is where reflection hides", and the whole Vixen.Rendering and Vixen.Net families. So the
# reason each of these eleven is here is now a MEASUREMENT and not a guess: rooting all sixty-six at
# once produced exactly twelve ILC findings, and they are quoted below.
#
# ⚠ Vixen.Xr and Vixen.Xr.OpenXR left this list on 2026-09-10 (#1239), and their six findings with
# them. They were here for one call site — `XR.GetApi()` — and the cure was the thirty lines
# VulkanLoader and OpenALLoader already had, written a third time as
# Platform/Vixen.Xr.OpenXR/OpenXrLoader.cs. So six of the twelve findings below are gone and the
# remaining six are all in Vixen.Ui and Vixen.Ui.HotReload. ⚠ What that publish proves is that ILC
# stops complaining, and not that OpenXR still initialises: this repository has no XR device.
#
# ⚠ Vixen.Ui and its six siblings — .Controls, .Controls.Advanced, .Markup, .Renderer, .Desktop and
# Vixen.Platform.Ui — left this list on 2026-09-22 (#1240). They were here for ONE finding, the IL2072
# in UiPropertyRegistry.Collect, and it was a true positive: the walk forced every base type's class
# constructor through Type.BaseType, which ILC cannot name, so a NativeAOT build silently lost every
# property a base class declared. Rooting all seven then published with zero ILC findings (win-x64,
# warnings as errors, a 46.7 MB native binary that runs). So 91 of 95 are rooted and the four left
# are here because no shipped game links them, not because of anything ILC said.
#
# ⚠ The cure has since changed, and this file is where a reader looks before touching that rooting.
# #1240's cure was in Vixen.Ui.Generators — each generated static constructor runs its nearest
# property-declaring ancestor's by typeof — with UiPropertyRegistry forcing only the leaf. That left
# a leaf declaring nothing of its own, which gets no generated constructor, answering without its
# bases. #1336 put the registry's own walk back and made it legal with
# DynamicallyAccessedMemberTypes.All on Of/TryFind/Collect, which is the one annotation ILC
# propagates across Type.BaseType intact. So the registry forces EVERY level again, and those three
# attributes are what keeps Vixen.Ui off this list: measured 2026-09-23, reverting the one on
# Collect to NonPublicConstructors is IL2059 + IL2072 out of ILC — and zero warnings out of an
# ordinary `dotnet build`, which is why CheckAot is the only thing that can see an edit to them.
#
# The `-ios`, `-android` and `-browser` heads and the netstandard2.1 generators are out of scope by
# target framework — `CheckAotIos` is the gate over the iOS one.
